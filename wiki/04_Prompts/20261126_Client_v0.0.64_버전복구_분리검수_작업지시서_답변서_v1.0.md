## 1. 종합 의견

작업지시서의 진단과 권고에 **동의**합니다. 특히 아래 두 지적은 정확했습니다.

- **"버전 사고 복구와 4환경 분리 정착이 겹쳤다"** → 실제로 제가 버전만 역행시키고 기능 커밋은 보존했으며, 환경 분리 규약은 Server에서만 확정된 상태였다.
- **"복구 빌드라도 TEST 검수 후 DEV 승격"** →现行 Client에는 `test/*` 브랜치가 없어 이 절차가 빠져 있었다.

다만 **이미 수행된 작업과 지시서 권고 간 차이**가 있어, 아래에 사실대로 회신합니다.

## 2. 질문별 회신

### Q1. `git fetch --all --prune` 후 dev/prd 최신 커밋/태그/버전 실제값

| 항목 | 값 |
|---|---|
| fetch 결과 | **실패** (`dev`, `prd` 모두 SSH 4949 timeout) |
| dev/prd 최신 (cached ref) | `df9432cc` |
| 태그 | `macos-v0.0.63` (df9432cc), 이하 `macos-v0.0.62/61/60/59` |
| 해당 pubspec | `version: 0.0.63+64` |

즉 **지시서에 적힌 값과 동일**합니다. fetch는 실패했지만 cached ref가 최신으로 남아 있어 값 자체는 신뢰 가능.

### Q2. `df9432cc` 이후 선행 커밋과 기능 유실 위험

```
6d232e0a  v0.0.64 버전 복구 + 6700 트랙누적 수정 문서
aac71569  6700 재입장 원격 트랙 누적 근본 수정 (v0.0.58로 잘못 기재)
df9432cc  v0.0.63+64 (dev/prd 기준)
```

- **기능 유실 없음.** df9432cc의 선행 기능(TEST 프로파일, manifest 서버동기화)은 그대로 부모로 남아 있고, 그 위에 트랙 누적 수정만 추가됨.
- 문제는 **버전 번호만 역행**했던 것(现已 0.0.64+65로 복구).

### Q3. 작업 브랜치를 `test/*`로 분리할지 여부

**원칙에는 동의하나, 현재는 미분리 상태입니다.**

- 로컬/origin HEAD: `feature/external-network-access @ 6d232e0a` (v0.0.64+65)
- Client repo에는 지시서 권고한 `test/client-v0.0.64-recovery` 브랜치가 **아직 없음**
-NAS 4949 미도달로 `test/*` 브랜치를 origin에 push해도 검수용 원격 확보 불가

→ **다음 작업으로 `test/client-v0.0.64-recovery` 분리 후 origin push** 진행 예정. 단, 이미 origin feature 브랜치에 v0.0.64 커밋이 올라간 상태라, 분리 브랜치는 그 커밋을 base로 생성하는 방식이 안전함.

### Q5. 검수 계획 (6700 재입장 재현/해결 증거, 로그, SHA256)

- **구현 완료**: `SipProvider.onCallEnded` → `MediaProvider/MediaManager.clearRemoteSessions()`, 동기화 단계 트랙 3개 제한
- **실기 검증 대기**: v0.0.64 설치 후 6700 입장/퇴장 3회 반복
  - 기대: `Track is nil` 0건, 원격 track ≤3, 408 미발생, `ice=Completed`, `videoBytes>0`
- 증거 위치: `/volume1/NetBackup/보관함/개발/Live_Log/{1102,1103,1104}.txt`, `docker logs kibal-dev-asterisk`, `pjsip show channelstats`
- wiki 기록: `wiki/08_Experiments/20261126_6700재입장_트랙누적_검증기록_v1.0.md` (구현 완료/실기 대기 상태)

### Q6. NAS dev/prd push 가능 여부

**불가.** `ping 192.168.11.2`는 응답하나 **TCP 4949 closed** (SSH 서비스 미기동/방화벽). SMB(139/445), DSM(5000/5001)은 열려 있음. `git push dev/prd`는 SSH 4949를 사용하므로 timeout.

→ SKIP 사유 기록 완료. NAS SSH 복구 후 재푸시 필요.
