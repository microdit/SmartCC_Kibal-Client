## 2. 실측 결과

### 2.1 OPS 전면 hang (재발)

| 대상 | 실측 |
|------|------|
| `http://192.168.11.5:8091/health` (내부) | **HTTP 000 (6.0s timeout, 0 bytes)** |
| `http://appletreeda.synology.me:8091/health` (외부) | **HTTP 000 (6.0s timeout, 0 bytes)** |

→ OPS 컨테이너가 **다시 hang**. 이전 진단(20261120_OPS8091_hang_...)과 동일 패턴. 재시작으로 복구됐으나 **재발**.

### 2.2 hang 이전/이후 엔드포인트별 응답 (OPS 정상 시점 기준)

| 엔드포인트 | /health | /api/client/config | /api/client/contacts | /api/client-logs (POST) |
|-----------|---------|-------------------|---------------------|------------------------|
| 응답 | ✅ 200 | ✅ 200 (with key) | ❌ hang (0 bytes) | ❌ hang (0 bytes) |
| 용도 | liveness | 설정 조회 | 인증 검증 | 로그 업로드 |

→ `/health`와 `/api/client/config`는 정상, **`/api/client/contacts`와 `/api/client-logs` (POST)는 hang**. 서버 측 핸들러 데드락/블로킹 의심.

### 2.3 클라이언트 영향

- `_verifyAgainstServer` → `GET /api/client/contacts` → hang → "서버 연결 실패" → 인증 실패
- `_post` → `POST /api/client-logs` → hang → SocketException → 로컬 보관 후 재시도
- `refresh` → `/api/client/config` → 정상이지만, https 후보가 먼저 hang(6s) → 후보 순회 지연

## 3. 근본 원인 (추정)

1. **OPS 컨테이너 hang 재발**: `/health`까지 무응답 → 프로세스/컨테이너 레벨 데드락. 이전 "재시작으로 복구"는 임시 처방.
2. **엔드포인트별 hang**: `/contacts`, `/client-logs` 핸들러가 특정 조건(확장번호 1102, 또는 DB/파일 락)에서 블로킹. `/config`는 정상 → 핸들러별 문제.

---

## 4. Mac Pro 측 조치 요청

1. **OPS 컨테이너 재시작** (즉시): `docker restart kibal-ops` (또는 compose restart)
2. **`/api/client/contacts` 핸들러 점검**: 1102 확장번호로 호출 시 hang 재현 확인, DB 쿼리/락 점검
3. **`/api/client-logs` POST 핸들러 점검**: 대용량/특정 페이로드에서 블로킹 여부, 타임아웃/백프레셔 확인
4. **healthcheck + 자동 재시작 정책**: hang 감지 시 자동 재시작 (docker healthcheck + restart: unless-stopped)
5. **로그**: hang 발생 시점의 OPS 컨테이너 로그 수집 요청

## 5. 클라이언트 측 우회 (이미 적용)
