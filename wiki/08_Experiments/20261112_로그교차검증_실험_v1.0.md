## 1. 가설

- H1: 제공된 "1103 로그"는 실제로 1102 로그다.
- H2: 클라이언트(KST)와 Asterisk(UTC)는 9시간 차이이며, 404 시각이 서버 로그에 대응한다.
- H3: 404는 다이얼플랜/코덱이 아니라 1103 AOR의 contact 부재다.
- H4: `01:05:30`의 착신은 1103이 아니라 1102의 self-call이다.

---

## 2. 방법

```bash
# ① 덤프 파일 검증
python3 -c "확장자/줄수/첫·마지막 6줄 출력"

# ② 실행 중 컨테이너 로그
docker exec kibal-dev-asterisk sh -c \
  'grep -n -m 40 -E "Could not create dialog|404|1103" /var/log/asterisk/messages'

# ③ 인증 이벤트(AccountID/SessionID 포함)
docker exec kibal-dev-asterisk sh -c \
  'grep -n -m 8 -E "2026-11-11 16:0[45]" /var/log/asterisk/security'

# ④ OPS 수집 로그
docker exec kibal-dev-ops sh -c 'ls -la /var/lib/kibal-ops/client-logs/'
docker exec kibal-dev-ops sh -c \
  'grep -n -m 20 -E "01:05|404" /var/lib/kibal-ops/client-logs/1102.log'
```

## 3. 결과

### 3.1 H1 — 로그 정체 ✅

| 항목 | 값 |
|------|-----|
| 제공 로그 identity | `usr=1102@192.168.0.3 host=atomui-MacBookPro.local ip=192.168.0.4` |
| OPS `1102.log:249-267` | 제공 로그 `01:05:02~01:05:19` 구간과 **완전 일치** |
| OPS `1103.log` | 709,575 bytes, `host=AtomOppa ip=192.168.0.7`, `app=v0.0.13`, 별도 세션 |
| 로컬 `app.log` | `2026-11-12T21:17:09`, session `mwdij3x9-12xi1m4` (4줄) — 다른 세션 |
| 로컬 `app-prev.log` | `2026-11-12T20:20:15`, session `mwdghxb3-1i8qdam` (233줄) |

→ 제공 로그는 **OPS 수집본 1102.log**. 진짜 1103 로그는 별도 존재.

### 3.2 H2 — UTC↔KST 매핑 ✅

| 클라이언트 KST | 서버 UTC | 서버 이벤트 |
|----------------|----------|-------------|
| `01:05:02.134` | `16:05:02` | `ChallengeSent` / `SuccessfulAuth` `AccountID=1102`, `SessionID=tbfvf26b36uh2r533965` |
| `01:05:02.729` | `16:05:02` | `Could not create dialog to invalid URI '1103'` + `Failed to create outgoing session` |
| `01:05:18.940` | `16:05:19` | 2차 동일 (`SessionID=tbfvf7ln6ut8zb0ed70v`) |
| `01:05:29.986` | `16:05:30` | `callPressed target=1102` |

호 ID 앞 20자와 `SessionID`가 **정확히 일치** → 1102 INVITE 인증 성공 직후 Dial 실패가 404를 생성한 인과 확정.

### 3.3 H3 — contact 부재 ✅

```
messages:1261  [2026-11-11 16:05:02] ERROR res_pjsip.c: Endpoint '1103': Could not create dialog to invalid URI '1103'.  Is endpoint registered and reachable?
messages:1262  [2026-11-11 16:05:02] ERROR chan_pjsip.c: Failed to create outgoing session to endpoint '1103'
messages:1264/1265  [16:05:19] 동일 2회
```

- `extensions.conf:18` `Dial(PJSIP/${EXTEN},60,tT)` 정상 → 다이얼플랜 아님
- `pjsip.conf.template:227-242` 1103 endpoint 존재 → endpoint 미정의 아님
- 해당 시각 `security`에 `AccountID="1103"` 없음, `1103.log`에 기록 없음 → **미등록**
- `pjsip show contacts` 현재는 `1103`+`1201`만 `Avail` (`1102` 없음)

동일 오류 반복: `1002`(11-11 02:06/02:11/04:56), `1003`(03:11), `1102`(08:33), `1103`(11-09 23:18, 11-10 00:08/04:13) → **WebRTC 등록 유지 전반 문제**.

### 3.4 H4 — self-call ✅

`1102.log:269`: `[2026-11-12T01:05:29.986868] EVENT UI DIALER action=callPressed params=target=1102`

→ `01:05:30.507 direction=incoming`은 1103이 건 것이 아니라 **1102가 자기 번호로 건 호출**. 이전 분석의 "1103 생존" 추론은 기각.

## 5. 결론

가설 H1~H4 **모두 채택**. 404는 "1103 AOR에 유효 contact가 없는 순간의 `Dial(PJSIP/1103)` 실패"로 확정되었고, 분석의 출발점이었던 로그 귀속·타임존·착신 해석 3건이 바로잡혔다.

---

## 6. 재현 주의

- 서버 로그는 UTC, 클라이언트/OPS 로그는 KST. **9시간 차이를 항상 명시**한다.
- `pjsip set logger on`은 `full`(28MB)을 급증시키므로 진단 후 반드시 `off`.
- OPS 로그는 `keep_lines=2000` 로테이션 대상이므로 오래된 시각은 유실될 수 있다. `security`/`messages`를 1차 근거로 쓴다.
