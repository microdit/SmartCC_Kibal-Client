## 1. 검증 목적

주소록이 네트워크 변동/조회 실패 시 사라지지 않고, 서버 버전 변경 시에만 사용자 주도 갱신이 발생하는지 확인하기 위한 기준선과 테스트 시나리오를 정의한다.

## 2. 기준선 관찰(현행)

| ID | 시나리오 | 현재 관찰 | 근거 | 판정 |
|----|----------|-----------|------|------|
| B1 | OPS config가 내부 IP 반환(외부망) | config 200 후 내부 ws/domain/client_log_url 적용 가능 | 2026-11-21 Mac Pro 협의 의견서, `server_config.dart` refresh | 위험 |
| B2 | 내부 주소 적용 후 contacts/conferences timeout | `OpsDirectory.fetch()`가 빈 `OpsDirectory()` 반환 | `ops_directory.dart` | 위험 |
| B3 | 빈 디렉터리 반환 후 UI 반영 | `_refresh()`가 `_directory=OpsDirectory()` 및 `contacts=0 rooms=0` 상태 노출 가능 | `address_book_screen.dart` | 위험 |
| B4 | 앱 재개/설정 복귀/수동 새로고침 | `_refresh()` 호출 | `address_book_screen.dart` | 빈번 갱신 |
| B5 | 서버 버전 필드 존재 | `/api/client/config`에 `config_version`, `manifest.config_version` 존재 | `server/ops/api/app/routes.py` | 활용 가능 |

## 3. 목표 동작 검증 시나리오 (구현 후)

| ID | 시나리오 | 절차 | 기대 결과 |
|----|----------|------|-----------|
| T1 | 최초 인증, 캐시 없음 | 인증 완료 → 주소록 화면 진입 | 전체 fetch 1회, 캐시 저장, 주소록 표시 |
| T2 | 앱 재실행, 캐시 있음 | 앱 종료 후 재실행, 네트워크 정상 | 캐시 즉시 표시, 전체 fetch 없음, 버전 메타만 확인 |
| T3 | 네트워크 일시 단절 | 캐시 표시 상태에서 Wi-Fi/LAN 끊김 | 기존 주소록 유지, 빈 목록으로 바뀌지 않음 |
| T4 | 서버 조회 실패 | contacts/conferences timeout/500 | 기존 캐시 유지, 오류 배너/재시도 표시, `0/0` 덮어쓰기 없음 |
| T5 | 서버 버전 동일 | meta 조회 결과 version 동일 | UI 변화 없음, 자동 전체 갱신 없음 |
| T6 | 서버 버전 변경 | OPS에서 연락처 수정 후 version 증가 | "업데이트 가능" 배너 표시, 사용자 클릭 전 캐시 유지 |
| T7 | 사용자 업데이트 성공 | 배너에서 업데이트 클릭 | 새 주소록 반영, version 갱신, 배너 제거 |
| T8 | 사용자 업데이트 실패 | 업데이트 중 네트워크 오류 | 기존 캐시 유지, 실패 안내 |
| T9 | 강제 갱신 발행 | OPS 콘솔에서 force publish | 클라이언트가 force 안내/자동 반영, force_version 기록 |
| T10 | 외부망 내부 config 오염 | 외부 프로필에서 config가 내부 IP 반환 | 오염값 거부 또는 무시, 기존 캐시/외부 프로필 유지 |
| T11 | 미인증 상태 | 키/인증 없음 | 인증 안내, 캐시 정책에 따라 미노출 또는 보호된 표시 |

## 4. 관찰 포인트

- 로그: `AddressBook synced ...`, `OPS directory: ...`, `서버 설정 갱신 ...`, `OPS directory fetch failed ...`
- 파일: `<logs>/server-config.json`, `<logs>/address-book-cache.json`(구현 후)
- UI: 주소록 건수, 배너 문구, 마지막 동기화/버전 표시
- 서버: `/api/client/config`의 `config_version`, `manifest`, `force_version`(구현 후)

## 5. 합격 기준

- T3/T4/T8에서 기존 주소록 건수가 유지된다.
- T2/T5에서 전체 contacts/conferences fetch가 발생하지 않는다(또는 정책상 meta만 발생).
- T6에서 자동 덮어쓰기 없이 사용자 액션이 필요하다.
- T9에서 강제 갱신만 자동/강제 흐름을 탄다.
- T10에서 내부 IP 오염으로 주소록이 소실되지 않는다.

## 6. 미실행/제약

- 본 문서 작성 시점은 **설계/기준선 기록**이며, 버전관리 구현 전이다.
- T1~T11은 구현 후 macOS/Windows 클라이언트와 OPS 서버에서 실기 검증 필요.
- 외부망 config 오염(T10)은 서버 수정과 클라이언트 가드가 함께 필요할 수 있다.
