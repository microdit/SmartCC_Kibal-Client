## 1. 총평

외부 보고서의 핵심 판정은 타당하다.

- 영상 미수신의 직접 원인을 **ConfBridge SFU re-INVITE 미응답(H5)** 으로 특정한 것은 서버 pjsip 로그와 일치한다.
- v0.0.8의 `onNewReinvite` 자동 수락과 `upgradeToVideo` 중복 방지도 코드와 일치한다.
- 다만 **인과 확정은 아직 아니다.** "re-INVITE를 수락하면 서버가 영상 RTP를 송신한다"는 것은 v0.0.8 실기에서 `Sent RTP ... (type 100)`로 확인해야 한다.
- 또한 보고서가 "MediaManager 체인 정상"으로 평가한 부분에서 **다중 영상 저장 단계의 결함**을 추가로 확인했다. 이는 H5를 고쳐도 3자 영상이 1개만 보일 수 있는 원인이다.

## 3. 수용 항목 (근거)

### 3.1 H5 = re-INVITE 미응답

- 서버 증거: `evidence/20261111-124756-remote-audio/90_docker_during_test.log`
  - `3295: INVITE ... CSeq: 18793 INVITE` (서버→클라이언트)
  - `3360: INVITE ... CSeq: 14230 INVITE`
  - 클라이언트 응답은 `100 Trying`뿐, 동일 CSeq의 `200 OK` 없음
- 코드: v0.0.7 이하 `sip_client.dart`의 `onNewReinvite(ReInvite event) {}` 빈 구현
- v0.0.8: `sip_client.dart:573` `onNewReinvite` → `event.accept({})` 자동 호출, `581` `_acceptReinvite`
- 클라이언트 로그: re-INVITE 직후 `remoteStreamAdded state=video=2` → 15~17초 후 `cause=Code: [408] ... ICE Connection Failed` (v1.4 `12:53:18.239` → `12:53:33.199`)

### 3.2 3 m-line SDP 해석

- 서버 re-INVITE(`3346`): `m=video 10190 ... a=sendonly` — 서버가 보내고 클라이언트가 받는 라인. 해석 정확.
- 표현 정정: "recvonly m-line 추가"가 아니라 **서버 offer는 `sendonly`, 클라이언트 answer가 `recvonly`**.
- 첫 번째 `sendrecv` video(10080)는 양방향이므로 "자신의 카메라만 송신"이 아니라 **서버도 송신 가능한 라인**으로 표현하는 것이 정확.

### 3.3 R2/R3/R4/R5

- R2: re-INVITE의 새 m-line에 새 `ice-ufrag`/`fingerprint`/`a=connection:new` 존재. 새 ICE/DTLS 세대 필요. 타당.
- R3: `remoteStreams`가 세션당 1개(`media_manager.dart:49-56`), `_videoStreamOfSession`이 첫 영상 스트림만(`334`), 렌더러도 세션 인덱스당 1개(`344`). 3자에서 타일 1개. 타당.
- R4: `sip_client.dart:686`이 `track.kind != 'audio'`를 skip. onTrack 복구는 kind 무관(`605-619`, `622`)이나 sweep fallback은 오디오만. 타당.
- R5: v1.4는 6000 회의만 기록. 1:1은 상대 미등록 480뿐. 타당.

## 4. 부분 수용 / 수정 항목

### 4.1 "영상 송신 0건의 직접 원인 = re-INVITE 미응답" — 유력 가설, 인과 미확정

- 현재 증거는 **상관관계**다: re-INVITE 미응답 상태에서 `Sent RTP ... (type 100)`가 0건.
- 인과 확정 조건: v0.0.8에서 200 OK 전송 후 `Sent RTP ... (type 100)`가 실제로 발생해야 한다.
- 따라서 문서 표현은 "직접 원인"보다 **"가장 유력한 원인(검증 필요)"** 가 정확하다.

### 4.2 "기존 ICE 세대도 실패" — 오디오 transport는 유지

- v1.4 첫 통화: `12:53:20.879 audioBytes=35,680` → `12:53:30.878 audioBytes=111,680` → `12:53:33.199` 종료.
- 즉 오디오 transport는 종료 직전까지 동작했다. 실패는 **새 영상 transport 및 집계 `connectionState`** 로 보는 것이 정확하다.

### 4.3 "원격 오디오 인바운드 정상" — 경로는 정상, 참가자 음성은 별도

- 안내음/효과음/서버 `Sent RTP type 00` + 클라이언트 `audioBytes` 증가로 **경로**는 정상.
- 서버 `Got RTP type 00`(1102/1103)로 참가자 오디오가 서버에 도달한 것도 확인.
- 다만 "상대방 음성이 들린다"는 것은 발화 구간 테스트로 별도 확인해야 한다.

### 4.4 R1(mid-less/BUNDLE → 488) — 가능성 낮음

- v1.4에서 클라이언트는 re-INVITE offer를 처리해 `remoteStreamAdded state=video=2`를 기록했다. `setRemoteDescription` 실패 로그 없음.
- 서버 로그에도 `SIP/2.0 488` 없음.
- 초기 answer(2 m-line)도 mid/BUNDLE 없이 수락되어 오디오가 흘렀다.
- 결론: **488이 실제 발생할 때 대응하는 조건부 리스크**로 낮춘다.

### 4.5 MediaManager "정상" — 단일 영상만 정상

- `addRemoteStream`의 중복 제거가 **첫 트랙 ID만** 비교한다(`media_manager.dart:304-309`).
- v1.4 `12:53:18.239` 로그: `event(video=2 audio=1)` 인데 `session(video=1 audio=1)` → 새 스트림이 통째로 버려져 **두 번째 영상 트랙 유실**.
- 상세는 6.1.

### 4.6 MCU 전환 — 최후 수단

- `video_mode=follow_talker`/`last_marked`는 다자간 영상 요구를 단일/활성 영상으로 축소한다.
- 프로젝트 목표(다자간 영상)와 상충하므로, SFU + 클라이언트 렌더러 개선을 우선하고 MCU는 fallback으로 둔다.

## 5. 비수용 항목

1. **R1을 주요 리스크로 보는 것** — 현재 증거(성공한 `setRemoteDescription`, 488 부재)와 배치된다. 조건부 리스크로만 유지.
2. **1:1 영상이 v0.0.8로 해결된다는 암시** — H5는 ConfBridge re-INVITE에서만 발생한다. 1:1 직접 통화는 별도 원인·별도 증거가 필요하다. 보고서 R5가 이를 인정하지만 §1 요약에서 혼합되어 있다.

## 6. 추가 발견 (보고서 누락)

### 6.1 [Critical] `addRemoteStream` 중복 제거가 새 영상 트랙을 폐기

**위치**: `macos-client/lib/src/media/media_manager.dart:304-309`

```dart
void addRemoteStream(MediaStream stream, String sessionId) {
  final list = _remoteSessions.putIfAbsent(sessionId, () => <MediaStream>[]);
  final firstTrackId = stream.getTracks().isEmpty ? null : stream.getTracks().first.id;
  final existsById = list.any((s) =>
      s.getTracks().map((t) => t.id).contains(firstTrackId));
  if (!existsById) list.add(stream);
```

- 새 이벤트 스트림의 **첫 트랙 ID**가 기존 스트림에 있으면, 새 스트림 전체를 추가하지 않는다.
- ConfBridge re-INVITE 후 새 원격 스트림은 `audio(기존) + video(기존) + video(신규)` 형태가 될 수 있고, 첫 트랙이 기존 audio이므로 **신규 video가 유실**된다.
- 증거(v1.4, `12:53:18.239`):
  - `event(video=2 audio=1)` (새 이벤트 스트림의 트랙 수)
  - `session(video=1 audio=1)` (저장된 세션 합계)
  - `streams=1` (스트림도 추가되지 않음)
- 영향: H5로 re-INVITE를 수락해도 **3자 두 번째 영상 트랙이 저장/렌더되지 않을 수 있다.**
- 권고 수정:
  - 중복 판정을 **전체 트랙 시그니처**(정렬된 track id 집합)로 변경하거나,
  - 스트림 단위가 아니라 **트랙 단위로 누적**하고, 영상 트랙별로 렌더 스트림을 구성.
- **구현 완료(v0.0.9)**: `addRemoteStream`을 전체 트랙 집합 비교로 변경하고, 영상 트랙별 렌더 스트림(`_syncRemoteVideoStreams`)을 도입. 실기 검증 대기.

### 6.2 [High] 세션당 영상 타일 1개 (R3 보강)

- `remoteStreams`(49-56)와 `_videoStreamOfSession`(334)이 **세션당 첫 영상 스트림 1개**만 반환.
- ConfBridge 3자는 **하나의 SIP 세션**이므로, 서버가 여러 영상 트랙을 보내도 타일은 1개.
- 권고: `Map<trackId, MediaStreamTrack>` 또는 영상 트랙별 `MediaStream`을 노출하고, 참가자 타일을 트랙 수만큼 생성. 라벨링은 SDP `mid`/`ssrc` 매핑이 가능해지면 참가자 식별과 연결.
- **구현 완료(v0.0.9)**: `remoteStreams`가 영상 트랙별 렌더 스트림 목록을 반환하도록 변경. ConfBridge 3자에서 타일 다중 표시 가능(실기 검증 대기).

### 6.3 [Low] `_scheduleReceiverSweep` audio-only (R4 확인)

- `sip_client.dart:686` audio만 sweep. 영상은 `pc.onTrack` 래핑(`605-619`)에 의존.
- `_recoverRemoteTrack`은 kind 무관하게 처리하므로 onTrack이 오면 영상도 복구된다. 다만 onTrack이 누락된 경우의 fallback이 없다.
- 권고: sweep에 video를 포함하거나, 영상 전용 복구 경로를 추가하고 `recovered=true kind=video` 로그로 확인.

### 6.4 [Medium] 1:1 인바운드 영상 경로 증거 부족

- `accept()`는 `mediaStream`을 전달하고 `buildCallOptions(voiceOnly)`를 사용한다(`sip_client.dart:310-323`).
- 코드상 영상 answer가 가능하지만, 실제 1:1 로그가 없다.
- 권고: 1102↔1103 1:1 영상 통화를 별도 수행하고 `SIP accept <- ... voiceOnly=false`, SDP `m=video`, `videoBytes`를 확인.

## 10. 결론

외부 보고서는 **H5 진단과 v0.0.8 수정 방향에서 수용**한다. 다만 다음 3가지는 반드시 보완해야 한다.
