## 1. 질문에 대한 답

> *"영상이 없는 사용자인 것을 식별하여 처리하는 것이 없나?"*

**식별하는 것은 이미 2계층에 있다. 그러나 그 결과를 ConfBridge의 발화자/영상 소스 선택에 반영하는 처리가 없다.**

| 계층 | 식별 근거 | 처리 |
|------|-----------|------|
| **OPS(서버)** | `server/ops/api/app/asterisk.py:195-198` — `core show channel`의 video stream `state ∈ (sendrecv, recvonly)` 로 `has_video` 계산, `/api/conference/<room>/participants` 응답에 포함(`:205`) | 참가자 목록에 `has_video` 제공 |
| **macOS 클라이언트** | `conference_participants.dart:41` `has_video` 파싱, `:152` 로그 `…:V / …:A` (`V`=영상, `A`=음성만), `conference_screen.dart:455,477,482` 영상 있는 참가자 우선 정렬, `:568` `_Placeholder.noVideo → '영상 없음 · 음성 참여'` 카드 | **카드에 "영상 없음" 표시** |
| **ConfBridge(서버 브리지)** | ❌ 없음 | `follow_talker`는 `Talking Threshold: 160` **오디오 DSP** 로만 발화자를 고르고(`confbridge show profile user kibal_user`), 해당 채널이 영상을 보내는지 보지 않는다 |

실기 로그가 이를 그대로 보여준다:

```
[01:43:37] CONFERENCE participants room=6100 n=1 [오세훈 서울시장 (1101):A*]
[01:47:39] CONFERENCE participants room=6100 n=2 [A10 회의실 (1201):V,오세훈 서울시장 (1101):A*]
```

`1101`은 `:A`(audio only)로 **정확히 식별**돼 있다. 그런데 이 정보가 브리지로 들어가지 않는다.

## 2. 왜 1201이 상대방 영상을 계속 기다리는가

```
1101 이 6100 첫 입장 (video=0, audio=1)
  └─ SIP call -> 6100 voiceOnly=true, mediaStream local video=0 audio=1
       └─ follow_talker 가 오디오 발화자로 1101 선택 (유일 참가자)
            └─ 1101 에게는 video 소스가 없음 → 브리지가 분배할 영상 RTP 0
                 └─ 1201 은 video-1 sendrecv/h264 로 협상 → 원격 프레임 기대
                      └─ RTP 프레임 0 → 스피너 무한 회전
```

- `1201`은 **SIP 단말(Yealink A10)** 이라 Kibal OPS `/api/conference/.../participants`를 조회하지 않는다. 즉 **`has_video=false`라는 식별 결과가 A10까지 전달되지 않는다.**
- A10은 `max_video_streams=1`이라 그 단일 `video-1` m-line이 비어도 대체 스트림이 없다.
- `Enable Events: yes`(G3)는 입·퇴장 **이벤트**만 켜고, 영상 소스 유무는 바꾸지 않는다.
- `confbridge.conf`에 `video_source`/빈 회의실 정지영상 미설정(선행 분석 10장).

⇒ **단절 지점 = OPS가 아는 `has_video`를 ConfBridge가 소비하지 않는다.**

### 실기 대조 (1101 로그)

| 시각 | `CONFERENCE participants` | 1101 수신 영상 |
|------|--------------------------|----------------|
| `01:43:37` | `n=1 [1101:A*]` (1101 단독) | `videoBytes=0` 전 구간 |
| `01:47:34` | `n=1 [1201:V]` (1201 먼저 있음) | `videoBytes=1418747 → 5542826` **정상 수신** |
| `01:48:28` | `n=3 [1201:V, 1101:A*, 1201:V]` | `videoBytes` 증가 → `01:50:23` 이후 `0` |
| `01:50:53`~ | — | `videoKB=0 decodedFrames+0 videoTracks=0/1` **수신 끊김** |

즉 **영상 있는 참가자(1201)가 발화자일 때는 영상이 흐르고, 영상 없는 1101이 유일/발화자일 때 0이 된다.** 마지막 행은 1101 본인도 영상 소스 부재의 영향을 받음을 보여준다(참가자 본인도 브리지 영상 슬롯이 비면 `videoTracks=0/1`).

## 3. 정정 — 1201 단독 입장 시 자기 영상

사용자 실기: *"1201 은 6100 첫 참석자인 경우 발언자, 자신의 영상이 큰화면에 나타난다. 지속된다."*

선행 분석보고서 v1.1 10장과 지식 K16은 `ConfbridgeSetSingleVideoSrc`의 *"distributed to all other participants"* 를 근거로 **"자기 영상은 자기에게 되돌려 보내지 않는다"** 고 썼는데, **`follow_talker` 자동 동작에는 적용되지 않는다.**

| 구분 | 동작 |
|------|------|
| `ConfbridgeSetSingleVideoSrc` (**AMI 수동 지정**) | 지정 채널의 영상을 *다른* 참가자에게만 분배 |
| `video_mode=follow_talker` (**자동**) | 현재 발화자 영상을 브리지에 올림 → **유일 참가자=발화자=자기 자신이면 자기 영상이 자기에게도 표시**(실기 확인) |

→ 정정: **단독 입장 스피너의 원인은 "자기 제외"가 아니라 "발화자에게 video 소스가 없을 때의 무한 대기"** 다. 1201(영상 있음) 단독이면 자기 영상이 보여 정상, 1101(영상 없음) 단독/발화이면 소스 0으로 스피너. `video_source` 미설정·`Enable Events` 는 부가 요인으로 유지.

## 4. 1:1 통화가 바로 종료되는 이유 (별개, 2가지)

### 4.1 발신 `1101 → 1201` = 404 (0.6초)

| KST | UTC | 근거 |
|-----|-----|------|
| `01:43:22.976` 404 | `16:43:22` | `Endpoint '1201': Could not create dialog to invalid URI '1201'` + `Failed to create outgoing session` + `app_dial.c: Unable to create channel of type 'PJSIP' (cause 3)` |
| `01:46:24.497` 404 | `16:46:24` | 동일 |

`pjsip show contacts`의 **`1201` = `Unavail` RTT `-nan`** → 재생성 후 A10이 재REGISTER 하지 않아 다이얼 가능 contact가 없음. (A3의 `remove_existing=no`는 1101~1104에만 적용, `[1201]`은 `max_contacts=1` + `remove_existing=yes` 유지 → `Unavail` contact가 남음.)

### 4.2 착신 `1201 → 1101` = 연결 1초 후 `BYE Received`

| KST | UTC | 근거 |
|-----|-----|------|
| `01:44:07.951 CONFIRMED` → `01:44:08.959 ENDED BYE` | `16:44:08` | `res_rtp_asterisk.c: Don't know how to send format h264 packets with RTP` |
| `01:47:03.855 CONFIRMED` → `01:47:04.834 ENDED BYE` | `16:47:04` | 동일 |

1101은 `voiceOnly=true`, `SIP accept video=recvonly`, `mediaStream local video=0`. A10(1201)은 H.264를 보내는데 1101 WebRTC leg로 전달 시 `Don't know how to send format h264 packets with RTP` → A10이 1초 만에 BYE. 선행 1:1 분석(1103 leg VP8 vs A10 H.264)의 **대칭 케이스**.

> 참고: 1101은 v0.0.24(F1 적용)인데 `SIP codec policy target=1201` 로그가 없다. `voiceOnly=true`라 offer의 video m-line에 H.264가 없어 `sdp_codec.dart:55` `if (h264.isEmpty) return section` → 변경 없음 → 로그 미출력. **F1 오작동이 아니라 정상 early-return** 이다.

## 5. 개선안 — 식별 결과를 브리지까지 연결

| ID | 내용 | 위치 | 효과 |
|----|------|------|------|
| **H1 (권장)** | OPS가 이미 계산한 `has_video`를 사용해, **`ConfbridgeSetSingleVideoSrc`를 영상 있는 채널로만** 호출하는 API/로직 추가. 영상 있는 참가자가 없으면 더미 소스 또는 이전 발화자 유지 | `server/ops/api/app/asterisk.py`(판정 재사용) + `routes.py`/AMI | **기존 자산 재활용**, 1101이 발화자여도 1201은 1201/더미 영상을 계속 받음 → 스피너 해소 |
| **H2** | 6100에 **정지영상 더미 채널 상시 입장** → 항상 영상 소스 ≥1 | dialplan/AMI | 스피너 해소(단 "영상 없음" 의미는 전달 안 됨) |
| **H3** | `follow_talker` 발화자 후보를 `has_video=true` 채널로 제한하도록 OPS가 AMI `ConfbridgeSetSingleVideoSrc` 주기적 갱신 + `talk_detect_events=yes` | `confbridge.conf` user profile | 오디오 전용 참가자가 발화자로 잡히는 것 자체를 회피 |
| **H4** | `video_mode=sfu` 전환 검토 | `confbridge.conf` | A10 `max_video_streams=1` 제약·6000 회귀 재검 필요, 범위 큼 |
| **H5 (운영)** | `1201` 재등록 + 6100 중복 1201 채널 정리(현재 `00000009`/`0000000c` + 6000 `00000005` = 3개) | 실기 | 404·중복 카드(`n=3 [1201:V, …, 1201:V]`) 해소 |
| **H6 (1:1)** | 1101처럼 `video=0` 단말과 A10 1:1 시 서버가 A10의 H.264를 WebRTC leg로 전달하지 않도록 코덱/방향 정합 처리 | 서버 SDP 협상 | 착신 1초 BYE 해소 |

> **핵심**: 새로 "식별"을 만들 필요는 없다. **이미 있는 `has_video`를 A10이 볼 수 있는 형태(브리지 영상 소스 선택)로 연결**하면 된다. A10은 OPS API를 못 보므로 서버가 대신 반영해야 한다.
