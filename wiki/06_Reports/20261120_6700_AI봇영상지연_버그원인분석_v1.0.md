| 항목 | 내용 |
|------|------|
| **작성일** | 2026-11-20 |
| **버전** | v1.0 |
| **증상** | 6700 회의실에서 AI봇(7001) 영상이 느리게 재생, 음성은 정상 |

## 1. 요약

AI봇 송출 자체나 Asterisk의 문제가 아니라 **1102 단말 구간의 영상 RTP 패킷 손실**이 원인이다. 오디오는 손실 0건으로 정상이고, 영상만 `freeze=324`, `pli=351`, `vLost=70,230`이 누적되며 5~30초 간격으로 프리즈·재생 지연이 반복된다.

---

## 2. 증상 및 로그 근거

### 2.1 1102 영상 통계 (14:27~14:37)

```
14:27:59 in=1280x720@24fps decodedFrames+79  keyframes=179 freeze=178 pli=204 vLost=38324
14:30:59 in=960x540@22fps  decodedFrames+100 keyframes=227 freeze=226 pli=253 vLost=48412
14:37:29 in=1280x720@5fps  decodedFrames+88  keyframes=325 freeze=324 pli=351 vLost=70230
```

| 지표 | 값 | 의미 |
|------|----|------|
| `audioLost` | **0** | 오디오는 무손실 |
| `vLost` | 70,230 (누적) | 영상 RTP 패킷 대량 유실 |
| `pli` | 351 (누적) | 수신侧이 키프레임을 계속 요청 |
| `keyframes` | 325 (누적) | 요청에 응답하며 키프레임 반복 전송 |
| `freeze` | 324 (누적) | 디코더가 연속 프레임을 못 받아 화면 정지 |
| `in fps` | 5~38fps, 자료 `-` | 프레임 도착이 불규칙 |
| `videoKB/30s` | 약 6,200~6,600KB | 약 1.7~1.8Mbps 수신(12Mbps 원본이 아님) |

### 2.2 1101 대조 (14:13~14:14, 같은 봇 스트림)

```
media summary 30s audioKB=184 videoKB=9057 audioLost=0 ice=Connected
video summary 30s in=1280x720@30fps decodedFrames+1486 freeze=0 pli=13 vLost=9
```

동일 봇·동일 ConfBridge에서 1101은 **30fps, freeze 0, vLost 9**로 정상이었다. 따라서 소스/서버 측 결함은 배제된다.

---

## 3. 원인 판정

### 3.1 배제된 원인

| 후보 | 판정 | 근거 |
|------|------|------|
| 봇 프로세스/세션 | 배제 | 단일 프로세스(PID 8396), `HEALTHY`, `diag-bot 7001 in 6700 video=live 1920x1080` |
| 봇 CPU/인코더 | 배제 | GPU Helper CPU 11%, 1시간 42분 안정 상주, 1101이 동일 스트림 정상 수신 |
| Asterisk 미디어 경로 | 배제 | `audioLost=0` 양방향, 1101 정상, ConfBridge 7001+1102만 존재 |
| 클라이언트 디코더 결함 | 가능성 낮음 | `vLost`/`pli`/`freeze`가 동시에 증가 → 수신 패킷 유실이 선행 |
| **1102 접속 구간(무선 링크 가능)** | **가장 유력** | 같은 방에서 1101(유선/동일 호스트)은 정상, 1102만 영상 손실 |

### 3.2 메커니즘

1. 진단봇 원본은 1920x1080/12Mbps이며, Asterisk가 1102에게 1280x720/약 2.5Mbps로 다운스케일해 전송한다.
2. 1102 구간에서 영상 UDP 패킷이 유실된다.
3. WebRTC가 PLI를 보내 키프레임을 요청하고, 송출 측은 키프레임을 재전송한다.
4. 키프레임 대기 중 디코더가 프레임을 출력하지 못해 `freeze`가 증가하고, 사용자는 "영상이 느리게 재생된다"고 인지한다.
5. 오디오(Opus)는 패킷 크기가 작고 FEC/PLC가 있어 `audioLost=0`을 유지한다 → **음성은 정상**.

---

## 4. 결론

**원인: 1102 단말 구간의 영상 패킷 손실 및 이에 따른 PLI/키프레임 반복 요청.** 봇·Asterisk·클라이언트 코드 결함이 아니다. 1102의 무선 링크 품질(또는 해당 단말의 Wi-Fi 수신 상태)이 가장 의심된다.

## 5. 후속 조치 제안

| 우선순위 | 조치 |
|----------|------|
| P1 | 1102 단말을 5GHz WiFi 또는 유선으로 전환 후 `video summary`의 `vLost` 증가 여부 재측정 |
| P1 | 진단봇 송출 해상도를 1280x720/2Mbps로 낮춰 링크 부하 완화(테스트 전용 콘텐츠이므로 화질 희생 가능) |
| P2 | 1102 수신 jitter buffer 상향 검토(WebRTC 기본값 조정) |
| P2 | OPS 일일 점검 보고서에 `vLost`/`freeze` 증가 임계치 알림 추가 |
| P3 | 무선 RSSI/재전송률 측정 및 AP 채널 간섭 점검 |

## 6. 유선 전환 검증 (원인 확정)

1102를 유선(`192.168.11.54`, 기존 무선 `192.168.11.59`)으로 전환하고 v0.0.39 → v0.0.40 재설치 후 6700 재입장 결과:

```
14:59:36 video summary in=1280x720@30fps keyframes=2 freeze=3 pli=1 vLost=0
14:59:36 media summary audioKB=188 videoKB=9109 videoTracks=1/1 audioLost=0 ice=RTCIceConnectionStateCompleted
```

| 지표 | 무선(변경 전) | 유선(변경 후) |
|------|------------|------------|
| IP | 192.168.11.59 | 192.168.11.54 |
| `vLost` | 70,230 누적 | **0** |
| `freeze` | 324 | 3 |
| `pli` | 351 | 1 |
| 수신 fps | 5~38, 자료 `-` | **30fps 안정** |
| ICE | Connected(손실) | **Completed** |

→ **무선 링크의 영상 패킷 손실이 원인임이 확정**되었다. 봇/Asterisk/클라이언트 코드 변경 없이 링크만 바꿔 정상화되었다.
