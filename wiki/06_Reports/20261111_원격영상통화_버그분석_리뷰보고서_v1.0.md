## 1. 요약 (Executive Summary)

**현재 증상(사용자 리포트)**
- 셀프 영상은 정상 출력
- 1:1 영상통화, 6000번 회의실 다자간 영상통화에서 **상대방 영상/음성 미수신**
- 6000번 입장 시 영문 안내음(ConfBridge announcement)은 들림
- 다른 참석자 입장/퇴장 시 효과음(confbridge-join/leave)은 들림
- 통화 종료 시 종료음도 들림
- 영상통화는 보통 **17~35초 후 강제 종료**

**핵심 판정**
- **원격 오디오 인바운드 경로는 정상**이다. 서버가 생성한 안내음/효과음 RTP가 클라이언트에 도달하고, 클라이언트 로그에서 `audioBytes`가 지속 증가한다.
- **원격 영상이 전혀 수신되지 않는 이유**는 서버가 영상 RTP를 한 번도 송신하지 않았기 때문이다(`Sent RTP ... (type 100)` 0건).
- **영상 송신이 0건인 직접 원인**은 ConfBridge(`video_mode=sfu`)가 참가자 영상 합류 시 본 클라이언트로 볂는 **re-INVITE**(3개 m-line)에 대해, 클라이언트(v0.0.7 이하)가 `100 Trying`만 본낸 뒤 **200 OK(SDP answer)를 전송하지 않았기 때문**이다.
- re-INVITE 미응답으로 인해 새로 추가된 영상 m-line의 ICE/DTLS가 성립하지 않고, 기존 ICE 세대도 실패하여 `ICE Connection Failed`로 통화가 종료되었다.
- 해당 원인은 **v0.0.8에서 `onNewReinvite` 자동 수락으로 수정 완료**되었으나, 실제 단말 3대를 대상으로 한 실기 재검증은 아직 완료되지 않았다.

## 2. 증상 ↔ 로그 매핑

| 사용자 증상 | 클라이언트 로그 | 서버 로그/SDP | 해석 |
|------------|----------------|---------------|------|
| 셀프 영상 노출 | `localStreamReady video=1 audio=1` | - | 로컬 미디어 획득 및 렌더 정상 |
| 영문 안내음/입장음/종료음 들림 | `SIP stats inbound audioBytes=...` 5초당 ~40KB씩 지속 증가 | `Sent RTP ... (type 00)` 다수 | 서버 생성 오디오 RTP가 클라이언트에 도달함 |
| 상대방 음성 안 들림 | 발화 구간은 측정 불가(통화가 짧음) | `Sent RTP type 00`은 혼합 오디오로 송출 중 | 다른 참석자의 음성이 Asterisk에 제대로 도달하는지 별도 확인 필요 |
| 상대방 영상 안 나옴 | `SIP stats inbound videoBytes=0` 고정 | **`Sent RTP ... (type 100)` = 0건** | 서버가 영상 RTP를 전혀 송신하지 않음 |
| 17~35초 후 통화 종료 | `cause=Code: [408], Cause: RTP Timeout, Reason: ICE Connection Failed` | re-INVITE 재전송 후 BYE | re-INVITE 미완료 → ICE 세대 실패 |

### 3.2 현재까지의 핵심 원인: H5

**서버 re-INVITE SDP 예시**(evidence/20261111-124756-remote-audio/90_docker_during_test.log)

```
m=audio 10024 UDP/TLS/RTP/SAVPF 0 8 111 102 101
a=connection:existing
a=setup:actpass
a=fingerprint:SHA-256 ...
a=candidate:Hac130002 1 UDP ... 172.19.0.2 10024 typ host
a=sendrecv
a=rtcp-mux

m=video 10080 UDP/TLS/RTP/SAVPF 100 96
a=connection:existing
a=setup:actpass
a=fingerprint:SHA-256 ...
a=candidate:Hac130002 1 UDP ... 172.19.0.2 10080 typ host
a=sendrecv
a=rtcp-mux

m=video 10190 UDP/TLS/RTP/SAVPF 100 99
a=connection:new           ← 새 ICE/DTLS 세대
a=setup:actpass
a=fingerprint:SHA-256 ...
a=candidate:Hac130002 1 UDP ... 172.19.0.2 10190 typ host
a=sendonly                 ← 클라이언트가 이 영상 스트림을 수신해야 함
a=rtcp-mux
```

- 첫 번째 영상 m-line(`sendrecv`)은 자신의 카 메라를 송신하는 라인.
- 두 번째 영상 m-line(`sendonly`)이 **다른 참석자의 영상을 수신**하기 위해 ConfBridge가 추가한 라인.
- 이 `sendonly` m-line이 성립되지 않으면 서버는 영상 RTP(`type 100`)를 전혀 본낼 수 없다.
- 클라이언트가 re-INVITE에 200 OK answer를 본낼지 않았으므로, 해당 m-line은 폐기된다.

**re-INVITE 미응답의 코드적 근거**

`macos-client/lib/src/sip/sip_client.dart` (v0.0.7 이하):

```dart
@override
void onNewReinvite(ReInvite event) {}
```

`sip_ua`는 `EventReInvite`를 앱 리스너에게 전달하고, 앱이 `event.accept(...)`를 호출해야 200 OK(SDP answer)를 전송한다. 빈 구현이었으므로 응답이 없었다.

**v0.0.8 수정**

```dart
@override
void onNewReinvite(ReInvite event) {
  final hasAudio = event.hasAudio ?? false;
  final hasVideo = event.hasVideo ?? false;
  AppLogger.instance.i(
      'SIP re-INVITE 수신 hasAudio=$hasAudio hasVideo=$hasVideo -> 자동 수락');
  unawaited(_acceptReinvite(event));
}

Future<void> _acceptReinvite(ReInvite event) async {
  final accept = event.accept;
  if (accept == null) return;
  try {
    final accepted = await accept(<String, dynamic>{});
    AppLogger.instance.i('SIP re-INVITE 응답 전송 accepted=$accepted');
  } catch (error) {
    AppLogger.instance.e('SIP re-INVITE 수락 실패: $error');
  }
}
```

## 4. 서버/네트워크 환경 검토

| 항목 | 설정/값 | 검토 |
|------|---------|------|
| ConfBridge | `video_mode=sfu` | SFU 모드는 참가자 추가 시 re-INVITE로 recvonly 영상 m-line 추가 → re-INVITE 처리가 필수 |
| Endpoint | `media_address=192.168.11.39`, `ice_support=yes`, `dtls_verify=fingerprint`, `media_encryption=dtls` | 현재까지 정상 동작에 필요한 최소 설정 |
| Transport | `external_media_address=192.168.11.39`, `local_net=10.0.0.0/8` | ICE 후보 보정과 함께 사용 중 |
| SDP 단점 | re-INVITE에 `a=group:BUNDLE`/`a=mid` 없음, 3개 m-line 각각 별도 포트 | libwebrtc 호환성 리스크(아래 R1) |
| RTP 포트 | `10000-10200/udp` 호스트 매핑 | 영상 추가 m-line에도 포트 할당 가능 |
| 영상 코덱 | VP8, H264 협상 가능 | 클라이언트 동일 환경이므로 코덱 불일치 가능성 낮음 |

## 5. 코드 리뷰 소견

### 5.1 적절한 수정

1. **`sip_client.dart` re-INVITE 자동 수락**
   - `onNewReinvite`에서 `event.accept({})` 호출 → 서버가 필요로 하는 200 OK answer 전송
   - 예외 시에도 통화를 깨지 않도록 `try/catch` + 로그만 남김
   - 평가: **적절**

2. **`packages/sip_ua` 포크: `upgradeToVideo` 중복 방지**
   - v1.4 로그에서 re-INVITE마다 `local video=2`가 반복적으로 추가되는 현상을 차단
   - 이미 로컬 영상 트랙/송신기가 있으면 업그레이드 skip
   - 평가: **적절**

3. **ICE 후보 보정이 re-INVITE 경로에도 적용됨**
   - `_processInDialogSdpOffer` → `_sdpOfferToWebRTC` → `_rewriteUnreachableIceCandidates` 호출 확인
   - re-INVITE의 `172.19.0.2` 후보를 `c=` 주소(`192.168.11.39`)로 교체
   - 평가: **적절**

4. **`MediaManager`/`MediaProvider` 원격 스트림 렌더링**
   - `addRemoteStream` → `_rebindAllRemoteRenderers` → `RTCVideoView` 체인 정상
   - 영상/음성 스트림 분리 보관(D2), 재협상 시 nil 스트림 크래시 방지
   - 평가: **정상**

### 5.2 잔여 리스크

| ID | 리스크 | 설명 | 확인 방법 |
|----|--------|------|-----------|
| **R1** | re-INVITE SDP에 `a=group:BUNDLE`/`a=mid` 없음 | Asterisk가 3개 m-line을 별도 transport로 전달. libwebrtc가 mid-less SDP를 수용하지 않으면 `setRemoteDescription` 실패 → `request.reply(488)` 후 통화 종료 | v0.0.8 실기 시 앱 로그 `SIP re-INVITE 수락 실패` 또는 서버 `SIP/2.0 488` 확인 |
| **R2** | 새 m-line은 `a=connection:new` + 새 fingerprint/ufrag | 기존 DTLS 연결을 재사용하지 않고 새 ICE/DTLS 세대가 필요. answer 생성 시 클라이언트가 올바른 transport/지문을 제시하는지 확인 | 서버 `Sent RTP ... (type 100)` 발생 및 클라이언트 `videoBytes>0` 확인 |
| **R3** | 복구된 원격 스트림이 단일 `MediaStream`에 모든 트랙 합침 | `RTCVideoView`는 스트림의 첫 번째 video track만 렌더. 3자 이상 SFU에서 여러 원격 영상을 한 번에 표시하려면 트랙별 렌더러 분리 필요 | 3자 실기 시 화면에 1명분 영상만 나오는지 확인 |
| **R4** | `_scheduleReceiverSweep`이 오디오 트랙만 대상 | `track.kind != 'audio' continue` 처리. 영상 트랙은 `pc.onTrack` 래핑에만 의존 | 영상 수신 시 `recovered=true kind=video` 로그 확인 |
| **R5** | 1:1 영상통화 실패 증거 부족 | v1.4 로그는 6000 회의만 기록. 유일한 1:1 시도는 상대 미등록으로 480 종료. re-INVITE는 ConfBridge에서만 발생하므로 1:1 실패 시 별도 원인 가능 | 1:1 영상통화 별도 실기 수행 |

## 6. 해결 방안

### 6.1 즉시 실행 (P0)

1. **v0.0.8 DMG를 3대(Mac Pro 1101, MacBook 1102, iMac 1103)에 설치**
   - `/Applications` 복사 권장
   - `xattr -dr com.apple.quarantine /Applications/macos_client.app` 실행

2. **재검증 A: 1101(음성) + 1102(영상) 2자 회의 6000, 5분 이상 유지**
   - 클라이언트: `SIP re-INVITE 수신 ... -> 자동 수락`, `SIP re-INVITE 응답 전송 accepted=true` 확인
   - 클라이언트: `videoBytes`가 0에서 증가 시작 확인
   - 서버: `Sent RTP ... (type 100, ...)` 발생 확인
   - 서버: `ICE Connection Failed` 0건

3. **재검증 B: 1101 + 1102 + 1103 3자 회의 6000, 5분 이상 유지**
   - 전원 `audioBytes`/`videoBytes` 증가
   - `confbridge list 6000`에 3명 모두 남아 있음
   - 3자 입장 시 1명이 튕기지 않음

4. **회귀 검증: 1101 단독 6000 입장 60초 이상 유지**
   - H5 이전 오디오 단독 정상 케이스가 깨지지 않았는지 확인

### 6.2 실패 시 분기 대응 (P1)

| 관찰 | 원인 후보 | 조치 |
|------|----------|------|
| `SIP re-INVITE 수락 실패` 또는 서버 `488` | libwebrtc가 mid-less 3 m-line SDP 거부 | `packages/sip_ua` 포크에서 `_sdpOfferToWebRTC`에 `a=mid` 자동 삽입, 또는 `BUNDLE` 그룹 추가 보정 |
| 200 OK 전송 후에도 `videoBytes=0` 지속 | ConfBridge SFU 영상 송신 문제 | 서버 `pjsip show channelstats`, `confbridge list`로 채널/비디오 소스 상태 점검. 필요 시 `video_mode=follow_talker` 등 MCU 모드로 임시 전환 검토 |
| 3자에서만 1명 튕김 | SFU 포트/ICE 충돌 또는 재협상 루프 | 참가자별 SDP/RTP 로그 분리, 채널당 ICE 후보/포트 중복 여부 확인 |
| 오디오 단독 회귀 | H5 수정 부작용 | 1101 단독 60초 테스트 즉시 수행, 로그 롤백 |

### 6.3 장기 개선안 (P2)

- **Asterisk ConfBridge SFU의 한계 인식**: Asterisk SFU는 re-INVITE 기반 다중 m-line 구조로 복잡하며, 클라이언트 WebRTC 엔진 호환성 이슈가 반복될 수 있음.
- **대안 검토**:
  - **MCU 모드**: `video_mode=follow_talker` 또는 `last_marked`로 단일 혼합 영상 송수신 — 클라이언트/ICE 복잡도 감소, 화질/지연 트레이드오프
  - **전용 SFU 서버**: mediasoup, Janus, Pion 등으로 교체 — BUNDLE/mid 기반 단일 peerconnection, 표준 WebRTC 호환성 우수
- **운영**: DEV 환경에서 충분히 검증된 후 PRD 적용. `dtls_verify=fingerprint`는 DEV 한정이며 PRD 적용 시 인증서/CA 정책 재검토 필요.

## 8. 결론

사용자가 보고한 "원격 영상/음성 미수신 + 17~35초 후 종료"는 단일 원인이 아니라 여러 ICE/DTLS/SDP 처리 결함이 연쇄적으로 발생한 결과이다. 특히 영상이 전혀 안 오는 직접 원인은 **ConfBridge SFU의 re-INVITE에 클라이언트가 200 OK를 응답하지 않아 영상 m-line이 성립되지 않은 것**이다. v0.0.8에서 이를 수정했으나, 실제 단말 3대를 대상으로 한 5분 이상 장기 실기 검증이 남아 있다. 또한 Asterisk의 mid-less/BUNDLE 없는 3 m-line SDP, 3자 이상 SFU 다중 영상 렌더링, 1:1 영상통화 별도 증거 부족 등은 후속 검증과 개선이 필요한 잔여 리스크이다.
