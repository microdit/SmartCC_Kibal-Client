## 1. 요약

2026-11-05 PRD 점검과 SSH 장애 분석에서 확인된 보안 이슈를 정리했다. 이 보고서는 **Synology Security Advisor 또는 외부 취약점 스캐너의 공식 결과가 아니라**, 현재 구성과 로그를 직접 확인한 수동 보안 권고다.

### 핵심 판정

| 구분 | 건수 | 내용 |
|------|------|------|
| High | 3 | SSH 비밀번호 인증, 로컬 무인증 Docker API, 관리자 페이지 HTTP |
| Medium | 4 | 죽은 SSH hardening 설정, `StrictModes no`, SSH 서비스 hang, WS 평문 |
| Low | 3 | OpenSSH 버전·DSA host key, 감사 로그 보존, 보안 점검 자동화 부재 |

가장 시급한 조치는 다음 세 가지다.

1. Ops 관리자 페이지에 TLS를 적용하고 세션 쿠키 `Secure`를 켠다.
2. SSH를 키 인증 전용으로 전환하고 `AllowUsers`를 실제 계정으로 제한한다.
3. `127.0.0.1:2375` Docker socket proxy의 로컬 접근 권한과 감시를 강화한다.

## 3. 주요 발견

### 3.1 [High] SSH 비밀번호 인증이 활성화되어 있다

**증거**

```text
port 4949
passwordauthentication yes
pubkeyauthentication yes
allowtcpforwarding no
strictmodes no
authorizedkeysfile /etc/ssh/authorized_keys/%u
```

**문제**

- 키 인증을 사용 중이지만 비밀번호 인증도 함께 열려 있다.
- `AllowUsers`가 실제 적용되지 않아 접속 가능한 계정 범위가 제한되지 않는다.
- SSH 포트가 `0.0.0.0:4949`와 `[::]:4949`에 모두 listen한다.
- NAS가 LAN에 노출되어 있고, 다른 서비스와 동일한 계정 체계를 공유한다.

**권고**

- `PasswordAuthentication no`
- `ChallengeResponseAuthentication no`
- `AllowUsers atom microdit009` 등 실제 필요한 계정만 명시
- 적용 전 별도 세션에서 키 인증을 확인하고, 적용 후 `sshd -T`로 검증

---

### 3.2 [High] 로컬에서 무인증 Docker API에 접근할 수 있다

**증거**

```text
kibal-prd-docker-proxy  tecnativa/docker-socket-proxy:0.2.0
127.0.0.1:2375->2375/tcp
```

proxy 환경:

```text
CONTAINERS=1
POST=1
EXEC=1
ALLOW_START=1
ALLOW_STOP=1
ALLOW_RESTARTS=1
SYSTEM=1
```

**문제**

- `2375`는 외부에 게시되지 않았지만 NAS 로컬에서는 인증 없이 접근 가능하다.
- `POST`, `EXEC`, `ALLOW_START/STOP/RESTARTS`가 열려 있어 로컬 비권한 계정이 Docker를 통해 권한 상승할 수 있다.
- NAS 계정이 하나라도 침해되면 컨테이너 생성·명령 실행을 통해 호스트 root 권한으로 이어질 수 있다.

**권고**

- NAS 로컬 계정 최소화 및 강한 인증 적용
- `2375` 접근 프로세스 모니터링(`lsof`, auditd 대체 로그)
- 가능하면 ops 전용 Unix socket + 그룹 권한으로 전환
- proxy 이미지 digest 고정 및 정기 업데이트

> 현재 host-network 우회는 Synology bridge 통신 문제 때문이며, 보안상 최선의 구성은 아니다. bridge 통신이 복구되면 컨테이너 네트워크 + 최소 권한 proxy로 재검토한다.

---

### 3.3 [High] Ops 관리자 페이지가 HTTP로 제공된다

**증거**

- `http://192.168.11.2:8091`
- `OPS_BIND: 0.0.0.0:${OPS_PORT:-8091}`
- `OPS_COOKIE_SECURE` 기본값 `false`

**문제**

- 관리자 세션 쿠키와 CSRF 토큰이 평문 HTTP로 전송될 수 있다.
- 같은 LAN의 공격자가 ARP spoofing/스니핑으로 세션을 탈취할 수 있다.
- `SameSite=Strict`, `HttpOnly`는 적용되어 있으나 `Secure`는 꺼져 있다.

**권고**

- Synology 역방향 프록시 또는 사내 CA로 HTTPS 종료
- `OPS_COOKIE_SECURE=1` 전환
- HTTP→HTTPS 리다이렉트
- 관리자 페이지를 신뢰된 관리 VLAN으로 제한

---

### 3.4 [Medium] `syno_security.conf`가 적용되지 않는 죽은 설정이다

**증거**

```text
/etc/ssh/sshd_config.d/syno_security.conf
PasswordAuthentication no
ChallengeResponseAuthentication no
AllowUsers atom microdit009
```

하지만 실제 `sshd -T` 결과에는 `allowusers`, `passwordauthentication no`가 없다. `/etc/ssh/sshd_config`에 `Include`가 없기 때문이다.

**문제**

- 보안 강화 설정이 적용된 것처럼 보이지만 실제로는 무효다.
- 운영자가 “이미 차단했다”고 오판할 수 있다.

**권고**

- `Include /etc/ssh/sshd_config.d/*.conf`를 추가하고 `sshd -t`로 검증
- 또는 파일을 제거하고 메인 설정에서 명시적으로 관리
- 설정 변경 후 반드시 `sshd -T`로 유효 설정 확인

---

### 3.5 [Medium] `StrictModes no`와 SSH 설정 드리프트

**증거**

- `/etc/ssh/sshd_config` mtime `2026-11-04 21:00:01`
- `LogLevel DEBUG`
- `StrictModes no`
- `Match User anonymous` 제거
- `AuthorizedKeysFile` 위치 이동

**문제**

- `StrictModes no`는 `authorized_keys`와 홈 디렉터리 권한 검사를 약화한다.
- `LogLevel DEBUG`는 불필요한 정보 노출과 로그 증가를 유발할 수 있다.
- 2026-11-04 21:00 변경 주체가 확인되지 않아 구성 드리프트 관리가 되지 않는다.

**권고**

- 키 파일 권한을 점검한 뒤 `StrictModes yes`로 복원
- `LogLevel INFO`로 환원
- sshd 설정을 Git 또는 문서로 관리하고 변경 시각·주체를 기록
- DSM 작업 스케줄러/패키지가 설정을 덮어쓰는지 확인

---

### 3.6 [Medium] SSH 서비스가 새 연결을 처리하지 못한 장애 이력

**증거**

- `09:57:03` 마지막 정상 세션
- `10:20:42` `sshd.service stop-sigterm timed out. Killing.`
- `sshd[9346]: fatal: recv_rexec_state: ssh_msg_recv failed`
- `status=9/KILL`

**문제**

- sshd 메인 프로세스가 `SIGTERM`에 90초간 응답하지 않았다.
- 장애 중 TCP 포트는 열려 있었지만 배너가 오지 않아 원격 관리가 불가능했다.
- journal 보존 기간이 짧아 트리거를 확정하지 못했다.

**권고**

- SSH 배너/포트 감시와 자동 알림 추가
- `journald` 보존 기간 확대
- DSM 외 복구 경로(물리 콘솔/별도 관리 포트) 확보
- OpenSSH 업데이트 검토

---

### 3.7 [Medium] SIP WebSocket이 평문이다

**증거**

- `OPS_WS_PORT=8088`
- `transport_ws: 0.0.0.0:8088/tcp`
- `ws://` 기반 LAN 구성

**문제**

- SIP 시그널링이 평문이면 내선 정보와 통화 메타데이터가 노출될 수 있다.
- 외부망 확장 시 WSS/TLS가 필수다.

**권고**

- LAN 우선 운영 시에도 WSS 적용 검토
- 외부망 확장 전 TLS 인증서, TURN, SRTP 포함 설계

---

### 3.8 [Low] OpenSSH 8.2p1 및 레거시 host key

**증거**

```text
OpenSSH_8.2p1, OpenSSL 1.1.1w
/etc/ssh/ssh_host_dsa_key (2019-07-25)
```

**문제**

- OpenSSH 8.2p1은 오래된 버전이다.
- DSA host key가 남아 있다. 최신 클라이언트는 DSA를 기본 비활성화하지만 불필요한 자산이다.

**권고**

- DSM 업데이트 또는 패키지로 OpenSSH 업그레이드 검토
- DSA host key 제거, RSA/ED25519 키만 유지

---

### 3.9 [Low] 감사 로그 보존·백업

**증거**

- `OPS_AUDIT_RETENTION_DAYS=90`
- 감사 로그는 `ops_audit` 볼륨에 JSONL로 저장
- 외부 SIEM/원격 백업 없음

**문제**

- NAS 손실/볼륨 손상 시 감사 로그가 함께 소실될 수 있다.
- 90일 이후 로그는 자동 정리된다.

**권고**

- 중요 이벤트는 원격 syslog/SIEM으로 전송
- 감사 로그 백업과 무결성 보관 정책 수립

## 5. 권고 우선순위

### P0 — 즉시

1. Ops HTTPS + `OPS_COOKIE_SECURE=1`
2. SSH 비밀번호 인증 비활성화 + `AllowUsers` 제한
3. `syno_security.conf` 적용 여부 결정 및 `sshd -T` 검증

### P1 — 1~2주

1. `StrictModes yes`, `LogLevel INFO` 복원
2. SSH 배너 감시·알림, journal 보존 확대
3. Docker proxy 로컬 접근 모니터링 및 최소 권한 검토
4. 외부망 확장 전 WSS/TLS/SRTP 설계

### P2 — 1개월

1. OpenSSH 업그레이드, DSA host key 제거
2. 감사 로그 원격 백업/SIEM
3. 정기 취약점 스캔과 구성 드리프트 점검
4. 비밀값 교체 주기와 보관 정책 수립

## 6. 검증 방법

| 항목 | 명령/확인 |
|------|-----------|
| SSH 유효 설정 | `sshd -T \| grep -Ei 'passwordauth\|allowusers\|strictmodes\|include'` |
| SSH 배너 | `timeout 3 bash -c '</dev/tcp/127.0.0.1/4949'` |
| Ops TLS | `curl -I https://<host>:8091` |
| 쿠키 Secure | 로그인 응답의 `Set-Cookie` 확인 |
| Docker proxy 노출 | `ss -lntp \| grep 2375` |
| 컨테이너 권한 | `docker inspect`의 `CapDrop`, `ReadonlyRootfs`, `SecurityOpt` |
| 감사 로그 | `/api/audit`, `ops_audit` 볼륨 |

## 7. 한계

- 이 보고서는 수동 구성 점검이며, 자동 취약점 스캔 결과가 아니다.
- Synology Security Advisor의 전체 점검 결과를 내보내어 대조하지 않았다.
- 외부 침투 테스트, 소스 코드 정적 분석, 모바일 앱 보안 점검은 포함하지 않았다.
- SSH 장애의 트리거는 로그 보존 한계로 확정하지 못했다.
- PRD는 현재 LAN 운영을 전제로 하며, 인터넷 노출 시 추가 위협 모델링이 필요하다.
