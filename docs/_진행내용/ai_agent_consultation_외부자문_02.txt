검토해 보니, 제안한 절차는 일부 방향은 맞지만 그대로 실행하면 안 됩니다. 특히 Method B 테스트와 영구 수정 단계에 구조적인 문제가 있습니다.

제 의견은 기존 Docker 환경을 유지하면서 테스트 방법과 영구 수정 방법을 분리하는 절충안입니다. Docker를 제거하거나 전체 구성을 다시 만드는 것은 필요하지 않습니다.

## 1. 전체 검토 결과

그대로 실행하면 안 되는 단계

| 단계                          | 검토     | 의견                                                        |
| --------------------------- | ------ | --------------------------------------------------------- |
| Step 0 컨테이너 확인              | 적절     | 이미 정상 실행 중인 컨테이너를 확인하면 됨                                  |
| Step 1 테스트 컨테이너 정리          | 적절     | 중단된 테스트 컨테이너만 정리                                          |
| Step 2 Method B 테스트 컨테이너 생성 | 부적절    | 기존 컨테이너와 네트워크를 공유하면서 Asterisk를 하나 더 실행하는 방식은 문제 발생 가능성이 큼 |
| Step 3 SIP 등록 테스트           | 수정 필요  | 환경변수 전달 방식에 오류가 있음                                        |
| Step 4 영구 수정                | 위험     | 실제 템플릿과 EntryPoint를 확인하지 않고 컨테이너 내부 파일을 직접 변경하고 있음        |
| Step 5 재시작 검증               | 방향은 적절 | 영구성 검증은 필요하지만 현재 수정 방식으로는 성공을 보장할 수 없음                    |
| Phase 2 통화 테스트              | 적절     | SIP 등록 성공 이후 진행                                           |

## 2. 가장 큰 문제: Step 2의 테스트 컨테이너

제안된 명령은 다음과 같습니다.

```
docker run -d \
  --name kibal-dev-asterisk-test \
  --network container:kibal-dev-asterisk \
  -e SIP_PASSWORD_1101=1101pass \
  smartcc-kibal-asterisk:dev
```

이 방식에는 중요한 문제가 있습니다.

`--network container:kibal-dev-asterisk`는 테스트 컨테이너가 기존 Asterisk 컨테이너의 네트워크 네임스페이스를 공유한다는 의미입니다.

따라서 두 번째 Asterisk가 실행되면 기존 Asterisk와 동일한 네트워크 인터페이스와 포트를 사용하게 됩니다.

현재 기존 컨테이너가 이미 다음 포트를 사용하고 있습니다.

- 5060/UDP
- 8088/TCP
- 10000\~10200/UDP

두 번째 Asterisk가 같은 포트에 바인딩하려고 하면 충돌할 수 있습니다.

실제로 제공된 실행 결과에서도 테스트 컨테이너가 `Exited (1)` 상태였습니다. 포트 충돌이 원인인지는 로그 확인이 필요하지만, 현재 방식의 구조적인 문제와 일치합니다.

따라서 이 테스트 컨테이너를 이용한 Method B는 채택하지 않는 것이 좋겠습니다.

## 3. Step 3에도 환경변수 전달 오류가 있습니다

기존 제안:

```
SIP_DOMAIN=192.168.11.39 SIP_WS_SERVER=ws://192.168.11.39:8088/ws SIP_PASSWORD=1101pass

node scripts/register-smoke.mjs
```

이 명령은 환경변수를 Node.js 프로세스에 전달하지 못할 수 있습니다.

다음처럼 한 명령에 붙여 실행하는 방식이 명확합니다.

```
SIP_DOMAIN=192.168.11.39 \
SIP_WS_SERVER=ws://192.168.11.39:8088/ws \
SIP_PASSWORD=1101pass \
node scripts/register-smoke.mjs
```

다만 실제 스크립트가 어떤 환경변수 이름을 사용하는지는 `register-smoke.mjs`와 `SipClient.ts`를 확인한 뒤 확정해야 합니다.

## 4. Step 4 영구 수정은 현재 방식으로 진행하면 안 됩니다

여기에는 세 가지 문제가 있습니다.

첫째, EntryPoint에 추가하는 명령이 잘못되었습니다.

제안된 코드:

```
: "SIP_PASSWORD_1101"="${SIP_PASSWORD_1101:-1101pass}"
```

이 코드는 변수의 기본값을 설정하는 명령이 아닙니다. `:` 명령에 인자를 전달하는 형태일 뿐입니다.

올바른 기본값 설정은 다음과 같은 형태입니다.

```
export SIP_PASSWORD_1101="${SIP_PASSWORD_1101:-1101pass}"
```

다만 이것도 실제 EntryPoint의 실행 순서와 변수 사용 위치를 확인한 다음 적용해야 합니다.

둘째, 컨테이너 내부 파일 직접 수정은 진정한 배포 관리 방식이 아닙니다.

```
docker exec kibal-dev-asterisk ...
```

이 방식으로 파일을 수정하면 현재 컨테이너의 쓰기 계층에는 남을 수 있지만, 컨테이너를 삭제하고 다시 생성하면 사라집니다.

따라서 호스트의 프로젝트 파일을 수정하고 Docker Compose의 `env_file` 및 필요하다면 `volumes`로 연결하는 것이 더 적절합니다.

셋째, `envsubst` 명령의 변수 목록을 임의로 지정하면 안 됩니다.

현재 제안에는 `1001~1004`, `1101~1104` 변수가 혼재합니다. 실제 템플릿에서 참조하는 변수와 일치하는지 확인해야 합니다.

무엇보다 중요한 것은 다음 두 설정의 차이입니다.

```
password=1101pass
```

```
md5_cred=...
```

- `password=`에는 SIP 클라이언트가 사용하는 평문 비밀번호가 들어가야 합니다.
- `md5_cred=`에는 단순한 MD5(password)가 아니라 해당 SIP 계정과 realm에 맞는 Digest 자격 증명이 들어가야 합니다.

따라서 현재 MD5 값이 문제인지 여부는 템플릿에서 해당 값이 어느 항목에 삽입되는지 확인해야 정확하게 판단할 수 있습니다.

## 5. 제가 권장하는 절충안

기존 Docker 컨테이너와 네트워크 구성을 유지하고, 다음 순서로 진행하는 것이 좋겠습니다.

## 권장 수정 절차

1. 기존 상태 보존 및 확인
   - 현재 컨테이너 상태와 로그 확인
   - 테스트 컨테이너 정리
   - 현재 Compose, Dockerfile, EntryPoint, PJSIP 템플릿 백업
2. 현재 설정의 원인 분석
   - `pjsip.conf.template` 확인
   - 실제 `/run/asterisk/pjsip.conf` 확인
   - `pjsip show auth 1101-auth` 확인
   - `pjsip show endpoint 1101` 확인
3. 평문 비밀번호 방식으로 테스트
   - 기존 Asterisk 컨테이너만 사용
   - 실제 템플릿에 `password=` 적용
   - 컨테이너 재생성 없이 설정을 반영하고 SIP 등록 확인
4. 영구 설정 반영
   - 호스트 프로젝트의 템플릿 수정
   - Compose 환경변수 설정
   - EntryPoint가 해당 변수를 정상적으로 읽도록 수정
5. 재시작 및 영구성 확인
   - 컨테이너 재시작 또는 재생성
   - 실행 설정 확인
   - 1101 SIP 등록 재검증
   - 1102 등록 및 양방향 통화 테스트

## 6. 추가로 반드시 확인할 사항

현재 문제는 1101과 1102의 오류 양상이 다릅니다.

| 계정   | 기존 오류      | 확인할 사항                        |
| ---- | ---------- | ----------------------------- |
| 1101 | SIP 500    | Asterisk 내부 오류, 설정 객체 및 서버 로그 |
| 1102 | SIP 401 반복 | 비밀번호, realm, Digest 인증 정보     |

그리고 1102의 WebSocket 접속 주소가 `192.168.11.2`로 나타났던 문제도 별도로 해결해야 합니다. 의도한 서버 주소는 `192.168.11.39`이므로 브라우저가 실제로 어느 주소에 접속하는지 확인해야 합니다.

1101의 500 오류와 1102의 401 반복을 하나의 MD5 문제로 단정해서는 안 됩니다.

## 최종 의견

저는 다음과 같이 결정하겠습니다.

- Docker 유지: 찬성
- 평문 `password=` 방식의 개발 테스트: 찬성
- 별도 테스트 컨테이너를 기존 네트워크에 연결: 반대
- 컨테이너 내부에서 EntryPoint를 직접 수정: 반대
- 호스트 프로젝트의 설정 파일을 수정하고 Compose로 영구 관리: 찬성
- 재시작 후 등록 테스트: 필수

그리고 한 가지는 분명히 말씀드리겠습니다. 현재 제 환경에서는 사용자의 Mac에 접속해 Docker 명령을 직접 실행할 수 없습니다. 앞서 제가 전체 작업을 직접 수행하겠다고 표현한 것은 정확하지 않았습니다. 대신 실제 실행 결과를 받아 분석하고, 확인된 결과에 따라 다음 명령을 제시하는 방식으로 진행할 수 있습니다.

우선 아래 네 가지 파일을 확인한 다음 수정에 들어가는 것을 권장합니다.

```
cd ~/Downloads/dev/SmartCC_Kibal-Client

echo "===== Docker Compose ====="
find . -maxdepth 3 \
  \( -iname 'docker-compose.yml' -o -iname 'compose.yml' -o -iname 'compose.yaml' \) \
  -print

echo "===== Dockerfile ====="
find . -maxdepth 4 -iname 'Dockerfile*' -print

echo "===== Entrypoint ====="
docker exec kibal-dev-asterisk \
  cat /usr/local/bin/kibal-entrypoint

echo "===== PJSIP Template ====="
docker exec kibal-dev-asterisk \
  cat /opt/kibal/config/pjsip.conf.template
```

이 결과를 기준으로 실제 파일 구조를 확인하고, 기존 동작을 보존하면서 최소한의 수정만 하는 것이 가장 안전합니다.
