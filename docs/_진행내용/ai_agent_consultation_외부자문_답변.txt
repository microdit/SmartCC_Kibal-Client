Asterisk Docker SIP Registration 장애 분석 및 해결 방안

해결 가능
 설정 영구화 필요

현재 제공한 로그와 설정을 기준으로 분석하면, 이번 문제는 단순히 SIP 비밀번호가 잘못된 문제가 아닙니다.

핵심은 Docker 컨테이너의 설정 생성 방식, Asterisk PJSIP 인증 구조, Web Client의 SIP 인증 정보가 서로 일치하지 않을 가능성입니다.

우선 다음 세 가지를 분리해서 해결해야 합니다.
1. Docker 환경변수와 PJSIP 설정 파일의 영구화
2. SIP Digest 인증의 정확한 구성
3. Web Client가 실제로 접속하는 Asterisk 서버 IP 통일
특히 한 가지 중요한 점이 있습니다.

SIP 클라이언트가 비밀번호의 MD5 해시를 직접 전송하는 것이 일반적인 SIP 인증 방식은 아닙니다. SIP Digest 인증에서는 서버가 401 Challenge를 보내고, 클라이언트가 nonce 등을 이용해 응답값을 계산합니다.

따라서 환경변수에 MD5 문자열이 들어 있다는 사실만으로 인증 실패 원인이라고 단정하면 안 됩니다.

1. 현재 장애의 원인 분석
1.1 증상별 원인 추정
증상	가능한 원인	우선순위
1101 - HTTP/SIP 500	PJSIP 설정 오류, endpoint/auth 참조 오류, 서버 내부 처리 오류	높음
1102 - 401 인증 반복	비밀번호 불일치, username/realm 불일치, MD5 계산 방식 오류	매우 높음
WebSocket 연결 성공	WS 전송 계층은 정상	확인됨
1102가 .2로 연결	오래된 Web Client 설정 또는 다른 서버 접속	높음
재시작 후 설정 초기화	컨테이너 생성 설정과 실행 설정의 차이	확인됨

참고로 SIP의 401은 최초 REGISTER 요청에서 정상적으로 발생할 수 있습니다.

정상적인 인증 흐름은 다음과 같습니다.
1. Web Client → Asterisk

REGISTER (Authorization 없음)


2. Asterisk → Web Client
401 Unauthorized
WWW-Authenticate: nonce, realm, algorithm


3. Web Client → Asterisk

REGISTER + Authorization Digest


4. Asterisk → Web Client
200 OK
Registration Successful


문제는 2번의 401이 아니라, 3번의 인증 응답을 서버가 거부하여 반복되는 상황입니다.
1.2 가장 중요한 인증 설정 오류 가능성
현재 컨테이너의 환경변수는 다음과 같습니다.
SIP_PASSWORD_1101=21b570670b1eec59ad5b90b76ee3a03b
SIP_PASSWORD_1102=3ab8f8012caee1cbab300ded5840ea6d


이 값들이 어떤 방식으로 생성된 해시인지 확인해야 합니다.

Asterisk PJSIP는 두 가지 방식을 지원합니다.
방식	PJSIP 설정	저장하는 값
일반 비밀번호	password=	실제 비밀번호
사전 계산 MD5	md5_cred= 또는 최신 버전의 password_digest=	username:realm:password의 MD5

예를 들어 다음은 서로 다른 값입니다.
# 잘못된 방식: 비밀번호만 MD5
echo -n "1101pass" | md5sum

# PJSIP MD5 인증용: username:realm:password
echo -n "1101:asterisk:1101pass" | md5sum


두 번째 계산 결과가 PJSIP의 MD5 인증용 값입니다.

따라서 현재 환경변수의 MD5 값이 단순히 비밀번호만 해시한 것이라면, md5_cred에 넣어도 인증되지 않습니다.

Asterisk 공식 문서에서도 이 차이를 명확하게 설명하고 있습니다. 

Asterisk Documentation+1

권장 결정: 현재 개발 단계에서는 MD5 사전 계산을 사용하지 말고 일반 비밀번호 방식으로 통일하십시오.

2. Q1: Docker 환경변수 영구 고정
권장 방법: Docker Compose
2.1 세 가지 방법 비교
방법	재시작 유지	권장 여부
docker exec 내부에서 수정	보장 안 됨	비권장
docker commit	이미지에 반영 가능	비권장
Docker Compose environment	컨테이너 재생성 후에도 유지	권장
Docker Compose env_file	컨테이너 재생성 후에도 유지	가장 권장

docker commit은 현재 컨테이너의 파일시스템 변경을 이미지로 저장하는 방식입니다. 환경변수와 실행 설정까지 관리하는 정상적인 배포 구조를 대체하지 못합니다.

또한 이미지 안에 계정 비밀번호를 저장하는 방식은 보안상 바람직하지 않습니다.
2.2 권장 디렉터리 구조
현재 프로젝트의 Docker 구성을 다음처럼 관리하는 것을 권장합니다.
SmartCC_Kibal-Client/
│
├── docker/
│   └── asterisk/
│       ├── Dockerfile
│       ├── docker-compose.yml
│       ├── .env
│       ├── config/
│       │   └── pjsip.conf
│       └── scripts/
│           └── entrypoint.sh
│
└── web/
    ├── .env
    └── src/


여기서 중요한 것은 다음 두 파일을 분리하는 것입니다.
- Docker .env: Asterisk 서버 계정 설정
- Web .env: 브라우저 SIP 클라이언트 설정
2.3 Docker 환경변수 파일
docker/asterisk/.env
SIP_PASSWORD_1001=1001pass
SIP_PASSWORD_1002=1002pass

SIP_PASSWORD_1101=1101pass
SIP_PASSWORD_1102=1102pass
SIP_PASSWORD_1103=1103pass
SIP_PASSWORD_1104=1104pass


위 비밀번호는 개발 환경 재현을 위한 예시입니다. 운영 환경에서는 별도의 강력한 비밀번호를 사용해야 합니다.
2.4 Docker Compose 설정
docker/asterisk/docker-compose.yml
services:
  asterisk:
    container_name: kibal-dev-asterisk

    image: smartcc-kibal-asterisk:dev

    restart: unless-stopped

    env_file:
      - .env

    ports:
      - "5060:5060/udp"
      - "8088:8088/tcp"
      - "10000-10200:10000-10200/udp"

    volumes:
      - ./config/pjsip.conf:/etc/asterisk/pjsip.conf:ro


주의할 사항:
- 실제 Asterisk 설정 경로는 이미지의 asterisk.conf와 Dockerfile을 확인한 후 확정해야 합니다.
- 현재 엔트리포인트가 /opt/kibal/config/pjsip.conf.template을 이용해 /run/asterisk/pjsip.conf를 생성한다면, 위 예시의 직접 마운트 방식 대신 템플릿을 마운트해야 합니다.
- 기존 컨테이너의 네트워크, 볼륨, 다른 포트 설정은 임의로 제거하지 말고 기존 Compose 설정에 병합하십시오.
2.5 컨테이너 재생성
Mac 터미널에서:
cd ~/Downloads/dev/SmartCC_Kibal-Client/docker/asterisk

docker compose config

docker compose up -d --force-recreate

docker ps --filter name=kibal-dev-asterisk


환경변수 확인:
docker exec kibal-dev-asterisk \
  printenv | grep '^SIP_PASSWORD_'


여기서 반드시 확인해야 할 점은 컨테이너가 재생성된 후에도 환경변수 값이 유지되는지입니다.

3. Q2: PJSIP 템플릿 영구 수정
권장 방법: 호스트 파일 관리 + Docker 마운트
3.1 왜 컨테이너 내부 수정이 유지되지 않는가?
현재 구조는 다음과 같이 추정됩니다.
Docker Image
smartcc-kibal-asterisk:dev

Entrypoint
/usr/local/bin/kibal-entrypoint

Template
/opt/kibal/config/pjsip.conf.template

Generated Config
/run/asterisk/pjsip.conf

Asterisk PJSIP Runtime


이 구조라면 /run/asterisk/pjsip.conf를 수정해도 컨테이너가 다시 시작될 때 템플릿으로부터 다시 생성됩니다.

따라서 수정해야 하는 대상은 실제 실행 파일이 아니라 원본 템플릿과 환경변수입니다.
3.2 먼저 실제 파일 경로 확인
다음 명령을 실행하십시오.
docker exec kibal-dev-asterisk sh -c '
echo "===== ENTRYPOINT ====="
cat /usr/local/bin/kibal-entrypoint

echo "===== TEMPLATE ====="
ls -l /opt/kibal/config/

echo "===== ASTERISK CONFIG ====="
ls -l /run/asterisk/

echo "===== PROCESS ====="
ps aux | grep asterisk
'


그리고 설정 파일의 경로를 확인합니다.
docker exec kibal-dev-asterisk \
  asterisk -rx "core show settings"


3.3 PJSIP 설정 수정 예시
개발 환경에서는 다음과 같은 형태를 권장합니다.

pjsip.conf:
[transport-ws]
type=transport
protocol=ws
bind=0.0.0.0:8088

; 1101
[1101-auth]
type=auth
auth_type=userpass
username=1101
password=1101pass

[1101]
type=aor
max_contacts=5
remove_existing=yes

[1101]
type=endpoint
transport=transport-ws
context=from-internal
disallow=all
allow=ulaw,alaw
auth=1101-auth
aors=1101

; 1102
[1102-auth]
type=auth
auth_type=userpass
username=1102
password=1102pass

[1102]
type=aor
max_contacts=5
remove_existing=yes

[1102]
type=endpoint
transport=transport-ws
context=from-internal
disallow=all
allow=ulaw,alaw
auth=1102-auth
aors=1102


1103, 1104도 동일한 구조로 추가합니다.

이 설정은 인증 구조를 설명하기 위한 예시입니다. 기존 설정의 transport 이름, context, endpoint 구성과 충돌하지 않도록 적용해야 합니다.

특히 auth_type=userpass는 기존 버전과의 호환성을 고려한 표기입니다. 최신 Asterisk에서는 auth_type=digest 사용을 권장합니다. 

Asterisk Documentation+1

3.4 템플릿을 호스트에서 관리하는 방법
Mac에서 원본 파일을 수정한 후 다음처럼 관리합니다.
mkdir -p docker/asterisk/config

# 원본 템플릿을 호스트로 복사
docker cp \
  kibal-dev-asterisk:/opt/kibal/config/pjsip.conf.template \
  docker/asterisk/config/pjsip.conf.template


수정 후 Compose에서 템플릿 경로를 마운트하도록 구성합니다.
volumes:
  - ./config/pjsip.conf.template:/opt/kibal/config/pjsip.conf.template:ro


이렇게 하면 컨테이너를 재생성해도 호스트의 템플릿을 사용합니다.

단, 엔트리포인트가 템플릿을 읽는 방식과 경로가 일치하는지 반드시 확인해야 합니다.

중요: docker cp만으로는 영구 수정이 되지 않습니다. 반드시 볼륨 마운트 또는 Docker 이미지 재빌드를 사용해야 합니다.

4. Q3: 1102의 IP 불일치 문제
별도 해결 필요
현재 가장 명확한 불일치가 발견됩니다.
항목	IP
Asterisk Docker 서버	192.168.11.39
Web Client .env	192.168.11.39
1102 WebSocket 접속 로그	192.168.11.2
NAS2 기존 주소	192.168.11.2

이것은 단순히 Asterisk 내부 인증 설정을 변경해서 해결할 문제가 아닙니다.

1102 클라이언트가 실제로 어느 서버에 접속하고 있는지 먼저 확인해야 합니다.
4.1 발생 가능한 원인
우선순위 순으로 살펴보면 다음과 같습니다.
1. 1102 클라이언트가 다른 PC 또는 브라우저에서 실행되고 있음
2. 이전 Vite 환경변수가 브라우저 빌드에 반영되어 있음
3. 브라우저 LocalStorage 또는 애플리케이션 설정에 이전 IP가 저장되어 있음
4. 다른 Web Client 인스턴스가 실행 중임
5. 프록시 또는 별도 WebSocket 서버를 경유하고 있음
특히 Vite 환경변수는 개발 서버가 시작될 때 읽히므로 .env를 수정한 것만으로 이미 실행 중인 클라이언트가 자동 변경된다고 가정하면 안 됩니다.
4.2 Mac에서 네트워크 확인
echo "===== Asterisk Server ====="

ping -c 3 192.168.11.39

echo "===== NAS2 ====="

ping -c 3 192.168.11.2

echo "===== WebSocket Port ====="

nc -vz 192.168.11.39 8088

echo "===== Old Server WebSocket ====="

nc -vz 192.168.11.2 8088


4.3 Web Client 설정 확인
프로젝트 루트에서 실행합니다.
cd ~/Downloads/dev/SmartCC_Kibal-Client

echo "===== SIP SERVER IP REFERENCES ====="

grep -RniE \
'192\.168\.11\.(2|39)|VITE_SIP_WS_SERVER|SIP_WS_SERVER' \
web/src web/.env web/.env.local \
--exclude-dir=node_modules


브라우저에서도 확인해야 합니다.
1. 개발자 도구(F12)
2. Network
3. WS 필터 선택
4. WebSocket Request URL 확인
5. 실제 접속 IP 확인
1102가 192.168.11.2로 접속하고 있다면 Web Client의 실행 환경부터 바로잡아야 합니다.
4.4 권장 네트워크 기준
Web Client
192.168.11.39:5173


Asterisk WebSocket
192.168.11.39:8088


Asterisk SIP
192.168.11.39:5060/UDP


모든 테스트 계정 1101~1104는 동일한 Asterisk 서버를 사용하도록 통일합니다.

현재처럼 IP 주소를 직접 사용한다면 DNS 변경은 필요하지 않습니다.

인증 객체의 이름이 존재하는 것만으로는 충분하지 않습니다. 실제 Endpoint가 그 인증 객체를 참조해야 합니다.
5.4 4단계: SIP 패킷 추적
이번 장애 해결에서 가장 중요한 작업입니다.

Asterisk CLI:
pjsip set logger on
core set verbose 5
core set debug 3


이 상태에서 1101로 로그인합니다.

정상적인 경우 다음 흐름이 나타나야 합니다.
REGISTER
    |
    v
401 Unauthorized
    |
    v
REGISTER + Authorization
    |
    v
200 OK


실패하는 경우 다음을 비교하십시오.
확인 항목	확인 내용
Authorization username	1101
Authorization realm	Asterisk가 발급한 realm
Authorization algorithm	MD5 또는 협상된 알고리즘
Authorization response	Digest 응답값
Asterisk Auth username	1101
Asterisk password	클라이언트와 일치
Endpoint InAuth	올바른 Auth 객체

주의: SIP 로그에는 인증 관련 정보가 포함될 수 있습니다. 외부에 로그를 공유할 때 Authorization 헤더와 비밀번호는 반드시 마스킹하십시오.
5.5 5단계: Web Client 재시작
cd ~/Downloads/dev/SmartCC_Kibal-Client/web

cat .env

# 기존 Vite 서버 종료 후 재실행
npm run dev -- --host 0.0.0.0


브라우저에서는 다음을 수행합니다.
- 기존 브라우저 탭 종료
- 개발자 도구에서 Application 확인
- 해당 사이트의 기존 LocalStorage 설정 확인
- Service Worker를 사용한다면 이전 캐시 제거
- 새로 접속하여 WebSocket 주소 확인
5.6 6단계: 1101부터 순차 테스트
순서	SIP ID	테스트 목표
1	1101	기본 인증 성공
2	1102	두 번째 계정 인증 성공
3	1103	세 번째 계정 인증 성공
4	1104	네 번째 계정 인증 성공

처음에는 반드시 1101 하나만 테스트합니다.

1101이 200 OK를 반환하면 1102를 추가합니다.
5.7 7단계: Docker 재시작 영속성 검증
이 단계가 완료되어야 이번 작업을 해결했다고 판단할 수 있습니다.
docker compose restart asterisk

sleep 5

docker ps --filter name=kibal-dev-asterisk

docker exec kibal-dev-asterisk \
  asterisk -rx "pjsip show endpoint 1101"


이후 1101~1104를 다시 등록합니다.

최종 합격 기준
- [ ] Docker 재시작 후 환경변수 유지
- [ ] PJSIP 설정 정상 생성
- [ ] WebSocket 연결 성공
- [ ] 최초 401 Challenge 정상
- [ ] 인증 응답 후 200 OK
- [ ] 1101~1104 모두 등록 성공
- [ ] 컨테이너 재생성 후에도 동일하게 동작
- [ ] 192.168.11.2로 접속하는 클라이언트 없음

6. Q5: 대체 접근 방식 및 최종 추천
네 가지 선택지를 비교하겠습니다.
선택지	장점	단점	평가
1. Docker 유지	재현성, 배포 편의성, 영구 설정 관리	초기 구성 정비 필요	추천
2. 직접 Asterisk 설치	설정 직접 관리 가능	macOS 환경 종속성, 운영 관리 복잡	비추천
3. 다른 SIP/미디어 서버	구조 변경 기회	재개발 및 검증 비용	현재 불필요
4. UI만 테스트	빠른 화면 검증	실제 SIP 기능 검증 불가	임시 대안

최종 추천: 1번 Docker 유지
현재 구성은 이미 다음과 같은 장점을 갖고 있습니다.
- Asterisk Docker 이미지 생성 완료
- WebSocket 연결 성공
- SIP 계정 1001~1104 구성
- RTP 포트 구성
- Web Client SIP 모듈 구현
- Smoke Test 스크립트 존재
현재 문제는 Asterisk 자체를 교체해야 하는 수준이라고 판단되지 않습니다.

오히려 Docker 설정의 영구화와 SIP Digest 인증을 바로잡는 것이 비용과 시간을 절약하는 방법입니다.

특히 프로젝트가 진행 중인 상황에서는 직접 설치로 전환하면 환경 차이 때문에 새로운 문제가 발생할 가능성이 있습니다.

7. 추가로 반드시 확인해야 할 사항
7.1 Vite의 SIP 비밀번호 보안
현재 Web Client 설정은 다음과 같습니다.
VITE_SIP_USERNAME=1101
VITE_SIP_PASSWORD=1101pass


Vite의 VITE_ 접두사가 붙은 환경변수는 브라우저에 전달되는 빌드 결과물에 포함됩니다.

따라서 SIP 비밀번호를 서버의 비밀정보처럼 보호할 수 없습니다.

개발 단계에서는 사용할 수 있지만 운영 환경에서는 다음을 권장합니다.
- 계정별 고유 비밀번호 사용
- SIP 서버 접근 네트워크 제한
- WebSocket을 운영 환경에서는 WSS로 전환
- 불필요한 SIP 계정 비활성화
- 운영용 계정과 개발용 계정 분리
7.2 1101의 500 오류는 별도 분석 필요
401과 500은 구분해서 처리해야 합니다.
- 401: 인증 Challenge 또는 인증 검증 문제
- 500: 서버 내부 오류 응답
500이 발생하는 시점의 Asterisk 로그와 PJSIP 설정 로딩 오류를 확인해야 합니다.

단순히 비밀번호를 수정한다고 500까지 해결된다고 보장할 수 없습니다.

8. 실제 작업을 위한 최종 실행 순서
제가 권장하는 진행 순서는 다음과 같습니다.
1. 현재 Docker 구성 백업
   
   Dockerfile, Compose, entrypoint, 템플릿을 확보합니다.
2. 인증 방식 단일화
   
   우선 1101을 plain-text password= 방식으로 변경합니다.
3. Docker 설정 영구화
   
   Compose env_file과 호스트 템플릿 마운트를 적용합니다.
4. 1101 단독 등록
   
   401 Challenge → Authorization → 200 OK 확인.
5. 1102~1104 확장
   
   동일한 인증 구조로 테스트합니다.
6. IP 통일
   
   모든 Web Client가 192.168.11.39:8088에 연결하도록 수정합니다.
7. 재시작 및 재현 테스트
   
   Docker 컨테이너 재생성 이후에도 등록 성공하는지 검증합니다.
9. 다음 단계: 실제 소스 기준 정밀 수정
현재 제공된 정보만으로 인증 실패의 원인 후보와 해결 구조는 상당 부분 좁힐 수 있습니다. 다만 실제 entrypoint와 템플릿을 확인하지 않은 상태에서 수정 명령을 확정하면 기존 Docker 구성을 손상시킬 수 있습니다.

다음 5개 자료를 기준으로 실제 수정안을 확정하는 것이 좋겠습니다.
번호	파일 또는 정보	확인 목적
1	docker-compose.yml	환경변수 영구화
2	Dockerfile	이미지 생성 구조
3	kibal-entrypoint	설정 초기화 원인
4	pjsip.conf.template	인증 객체 및 Endpoint 연결
5	register-smoke.mjs	클라이언트 인증 파라미터

Mac에서 다음 명령으로 수집할 수 있습니다.
cd ~/Downloads/dev/SmartCC_Kibal-Client

mkdir -p /tmp/kibal-sip-diagnostic

docker inspect kibal-dev-asterisk \
  > /tmp/kibal-sip-diagnostic/container-inspect.json

docker cp kibal-dev-asterisk:/usr/local/bin/kibal-entrypoint \
  /tmp/kibal-sip-diagnostic/entrypoint.sh

docker cp kibal-dev-asterisk:/opt/kibal/config/pjsip.conf.template \
  /tmp/kibal-sip-diagnostic/pjsip.conf.template

docker exec kibal-dev-asterisk \
  asterisk -rx "pjsip show endpoints" \
  > /tmp/kibal-sip-diagnostic/endpoints.txt

docker exec kibal-dev-asterisk \
  asterisk -rx "pjsip show transports" \
  > /tmp/kibal-sip-diagnostic/transports.txt

docker logs --tail 300 kibal-dev-asterisk \
  > /tmp/kibal-sip-diagnostic/asterisk.log 2>&1


여기에 프로젝트의 Compose 파일, Dockerfile, register-smoke.mjs를 추가하면 됩니다. 비밀번호, 인증 헤더, 토큰은 공유 전에 마스킹하십시오. 현재 파일 경로가 다르면 실제 경로를 사용해야 합니다.

최종 결론

이번 문제는 Docker를 포기하거나 Asterisk를 재설치할 필요 없이 해결할 수 있을 가능성이 높습니다.

제가 가장 권장하는 방향은 Docker Compose 기반 설정 영구화 → PJSIP 인증 정상화 → 1101 단독 등록 → 1102~1104 확장 → 재시작 검증입니다.

특히 첫 번째 목표는 1101에서 401 → 200 OK 흐름을 확실하게 성공시키는 것입니다. 이것이 성공하면 나머지 세 계정은 같은 구조로 확장할 수 있습니다.
