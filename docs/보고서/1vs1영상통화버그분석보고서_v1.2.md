## 1. 사용자 보고 증상

1. 1:1 연결은 됨. 1102는 1103의 영상·음성이 보이고 들림
2. **1103에서는 1102 영상이 안 보임**, 음성은 들림
3. 영상·음성이 끊기고 화질이 낮음
4. 영상이 정지된 채 보이다가, 1103에서 영상 끄기→켜기를 하면 1102로 영상이 다시 나감(리프레시 불량)
5. **21분 38초 후 자동으로 끊김**, 1103이 튕겨 나옴

## 2. 로그 수집 검증 (서버 vs 제출본)

| 단말 | 제출 파일 | 서버 수집(통화 구간, DEBUG 제외) | 판정 |
|------|-----------|-------------------------------|------|

- INFO+이벤트 모드 서버 수집은 신뢰 가능. 5초 통계(DEBUG)는 서버에 없음 → 정밀 분석 시 모드 상향 필요
- 서버 파일에 전송 타임아웃 재전송으로 **중복 줄** 발생(1102 26종, 1103 21종 ≈ 타임아웃 24/20회)

## 3. 원인 분석

### V1·V2 [확정·앱] 수신 측이 영상 전화를 음성 전화로 오인 → 단방향 영상

- 1102 로그: `SIP accept <- 1103 voiceOnly=true`, 로컬 `mediaStream video=0`
- 1103 로컬 통계: **영상 수신 바이트 259개 샘플 모두 0**(21분간 1102 영상 미수신)
- 코드:
  - `sip_ua_helper.dart:250` 수신 `Call` 생성 시 `hasVideo = session.data?['video'] ?? false` → 수신 세션은 `data['video']`가 설정되지 않아 **항상 voiceOnly=true**
  - `rtc_session.dart:264` 발신 `connect()`에만 `data['video']` 설정, `init_incoming()`에는 없음
  - `sip_client.dart` `accept()`: `voiceOnly = call.voiceOnly || ...` → 영상 offer에도 음성-only answer
- 외부 보고서 v1.0의 V1·V2를 실통화 로그로 **증명**

### V4 [확정·앱] 음성 수락 시 공유 로컬 스트림의 영상 트랙 제거

- `rtc_session.dart` answer 경로가 `mediaConstraints['video']==false`일 때 앱 공유 `mediaStream`에서 영상 트랙을 `removeTrack` → 셀프 프리뷰 소실 위험

### V5 [확정·앱+네트워크] 시그널링 요청 1회 타임아웃으로 통화 종료 (21분 후 튕김)

| 시각 | 출처 | 내용 |
|------|------|------|
| 18:40:19, 18:40:35 | 1103 | 로그 전송 `TimeoutException` |
| 18:40:57 | 서버 | 1102 Unreachable |
| 18:41:06 | 서버 | 1103 Unreachable |
| 18:41:13 | 1102 | `BYE Received` |
| 18:41:14 | 1103 | `408 Request Timeout` |

- 이 시각에도 음성 RTP는 흐르고 있었음(18:41:06 `audioKB=124`)
- sip_ua 기본 `session_timers=true`, 갱신 방식 UPDATE, 서버 `Session-Expires: 120;refresher=uac` → 발신자 1103이 갱신 담당
- `rtc_session.dart:1472 onRequestTimeout()`이 **in-dialog 요청 1회 타임아웃에 즉시 `terminate(408)`**
- 갱신 요청 종류(UPDATE)는 pjsip logger 미수집으로 정황 추정. 동작 자체(타임아웃 1회 = 종료)는 코드로 확정

### N1 [확정·네트워크] Wi-Fi 구간 손실·정체

- 1103 로컬 5초 통계: 음성 수신 패킷 **정상 대비 평균 69%**(시작 직후 98% → 2분 이후 42~77%)
- 1102 누적 음성 손실 약 35% → 양쪽 동일 수준
- MacPro→단말 ping: 1102 평균 23ms/최대 105ms, 1103 평균 44ms/**최대 382ms**, 1000B 패킷 1102 손실 2% (유선이면 1ms 미만)
- 통화 중 로그 전송(TCP) 타임아웃: 1102 24회, 1103 20회(거의 매분 수 초 정체)
- 서버 호스트 UDP 버퍼 드롭 0.04% → 서버 병목 아님
- 통화 초반 손실 적음 → 영상 비트레이트 상승 후 손실 급증: **영상 업링크 혼잡**이 양방향에 영향 가능

### C1 [확정·설정] 오디오가 ulaw(8kHz)로 협상

- 서버 WebRTC 엔드포인트 `allow` 순서가 `ulaw, alaw, opus` → ulaw 선택. 손실 은닉/FEC가 없어 같은 손실에서 opus보다 끊김이 크게 들림

### V6 [미확정] 영상 정지·리프레시 불량

- 1102는 영상 바이트가 계속 증가(2.8~3.9MB/30초)하는데 화면 정지 → **디코더가 키프레임 대기** 가능성
- 1103의 영상 끄기→켜기(18:39:19) 후 1102 영상 수신량 2.9 → 3.7~3.9MB/30초로 상승 → 토글이 새 키프레임을 만든 정황
- `framesDecoded`, `freezeCount`, `pliCount`, `nackCount`, `keyFramesDecoded`, 해상도, `qualityLimitationReason`이 로그에 없어 확정 불가

### D2 [확정·진단] 로그 전송 중복

- 타임아웃으로 클라이언트가 offset을 갱신 못한 채 더 넓은 구간을 재전송 → 서버는 시작 offset만 보고 겹친 앞부분을 다시 기록
