## 1. 리뷰 개요

본 리뷰는 Mac Pro 서버 작업 프롬프트와 작업계획서가 **"Mac Pro Agent가 그대로 실행할 수 있는 수준인가"**를 판정한다. 평가 축은 다음 4가지다.

1. **기술적 정확성** — 명령/가설/수정안이 Asterisk 22 및 현재 코드베이스와 일치하는가
2. **측정 가능성** — "audio 누락"을 증거로 확정·검증할 지표가 정의되었는가
3. **비교가능성** — 회귀 기준선(11-09)과 현재 증상이 동일 조건인가
4. **실행 안전성** — 통제·롤백·부작용 관리가 가능한가

### 1.1 종합 판정

| 문서 | 판정 | 등급 | 요지 |
|------|------|------|------|
| 프롬프트 v1.0 | **사용 부적합** | D | 기술 오류 3건 + 심각한 텍스트 손상. 원문 그대로 전달 불가 |
| 작업계획서 v1.0 | **조건부 승인** | B | 방향(Evidence-First, H1/H5 우선)은 타당. 기준선·측정지표·의사결정 분기 보완 필요 |

**결론**: 프롬프트 v1.0은 **폐기 후 v1.1로 재작성**, 작업계획서는 **v1.1로 보완 후 W1 착수**를 권고한다. 계획서의 골격은 재사용 가능하다.

## 3. 프롬프트 v1.0 지적사항

### 3.1 [P0] 심각한 텍스트 손상 — 실행 지시문으로 부적합

원문에 인코딩/OCR 수준의 손상이 다수 포함되어 있다. 지시문의 의미가 훼손되므로 **그대로 전달하면 오작동 위험**이 있다.

| 위치 | 원문(손상) | 추정 의도 |
|------|-----------|-----------|
| §1 제목 | "이 명인" | "의미인" |
| §3-1 | "m=audio 서셜 있습니다" | "m=audio 섹션이 있습니다" |
| §3-4 | "video no handling가 RTP video 협리만 두고 audio 안 뷰와 하는 경우" | 문장 복원 불가 |
| §5 | "적용한 scoreboard 변경 사항" | "설정 변경 사항" |
| §5 | "`video=1 audio=1` 도당" | "도달" |
| §6 | "단순 얼 눌击로" | "단순 오조작으로" |
| §6 | "다이렉트 서멍 조정" | 문장 복원 불가 |
| §6 | "client가 RID 가능성" | 문장 복원 불가 |
| §4-C | "client 단 (이미 v0.0.4 대응)" | 버전 근거 불명 |

**권고**: 프롬프트 v1.0 폐기, 아래 §6의 v1.1 체크리스트를 반영해 재작성. 손상 문장은 원저자 확인 후 복원.

### 3.2 [P0] 존재하지 않거나 잘못된 CLI 명령

| 원문 명령 | 문제 | 대체 |
|-----------|------|------|
| `pjsip show endpoint 6000` | 6000은 PJSIP endpoint가 아니라 dialplan extension/ConfBridge room | `dialplan show 6000@from-internal`, `confbridge list 6000`, `confbridge show bridges` |
| `rtp show rtcp stats` | 표준 Asterisk CLI에 없는 명령 | `rtp show settings`, `pjsip show channelstats`, `core show channels verbose` |
| `docker exec -it ...` | 비대화형/자동화에 부적합 (TTY 요구) | `docker exec kibal-dev-asterisk ...` |

### 3.3 [P0] 수정 우선순위 오류 — `video_mode=none`은 오디오 해결책이 아님

프롬프트 §4-A는 `video_mode`를 `none`으로 바꿔 오디오 누락을 검증하라고 지시한다. 그러나:

- `video_mode=none`은 **영상 브리지를 비활성화**하는 설정이다. 오디오 m-line 누락을 고치는 조치가 아니다.
- "video mode 활성화가 SDP renegotiation 시 `m=audio` 삭제/`a=inactive`를 유발한다"는 가설은 ConfBridge 동작상 근거가 약하다. audio는 별도 m-line으로 독립 협상된다.
- 결과적으로 이 A/B는 **영상만 죽이고 오디오는 그대로**일 가능성이 높아, 오진을 유발할 수 있다.

**권고**: `video_mode=none`은 **진단용 최후 수단**으로만, 그것도 "영상 유무가 오디오에 영향을 준다"는 SDP 증거가 있을 때만 사용. 최종 수정안으로는 금지(계획서 F3도 동일 입장 — 일치).

### 3.4 [P1] 비약된 결론 — "RTP 수신 뜨면 client 단"

프롬프트 §4-C는 "오디오 RTP 수신이 뜨면 client 단 문제"라고 단정한다. RTP 수신 여부만으로는 (a) 서버가 잘못된 코덱/포트로 보내는 경우, (b) DTLS-SRTP 복호화 실패, (c) 렌더 경로 누락을 구분할 수 없다. **판정 불가 → 추가 증거 필요.**

### 3.5 [P1] 재현 통제 부재

프롬프트는 1102/1103 동시 접속을 지시하지만, 버그분석 D3에서 확인된 **1102 중복 등록(iMac이 1102로 등록, 1103 미등록)** 상태를 통제하지 않는다. 이 상태로 테스트하면 원인 오판 가능성이 높다. 계획서 §8.1이 이를 보완하나, 프롬프트 단독으로는 미흡.

### 3.6 [P1] 롤백/원복 절차 부재

§4-A의 `sed -i`는 컨테이너 레이어 임시 변경이다. 재생성 시 유실되지만, 변경 후 원복·기록 지시가 없다. 계획서는 "결과 기록 후 원복"을 추가하여 보완(양호).

### 3.7 [P2] 기타

- §3-3의 SDP 캡처 형태 예시는 유용하나, **캡처 보관 경로/파일명**이 없다.
- "예상 소요 시간"이 조사 10분으로 과소 추정(디버그 로그 수집·분석 포함 시 부족).

## 4. 작업계획서 v1.0 지적사항

### 4.1 강점 (유지할 것)

- **Evidence-First 원칙**: 증거 없이 설정을 바꾸지 않는다는 원칙 명확.
- **가설 재우선순위화**: 클라이언트 H1/H5를 먼저 통제하고 서버 H2~H4를 좁히는 순서 타당.
- **CLI 정정**: 프롬프트의 잘못된 명령을 정확히 교정(§3.2 표).
- **git 이력 기반 반박**: `confbridge.conf`/`pjsip.conf.template` 변경 이력으로 "11-09 이후 서버 변경" 가설을 반박 — 검증 결과 사실과 일치.
- **롤백/리스크 표**, **테스트 시나리오(T1~T5)**, **산출물 정의**가 갖춰져 있음.

### 4.2 [P0] 기준선 버전 불일치

계획서 §3.3/§8.1은 기준선을 "v0.0.3 / `ce96203`"으로 기술하지만, 실제 `macos-client/pubspec.yaml`은 **`0.0.4+4`**이다. `ce96203`은 버전 문서 커밋일 뿐이며, 미디어 코드는 `8f2a8d0` 이후 상태다. F1 재검증 전 **정확한 빌드 커밋/버전을 확정·기록**해야 한다.

**권고**: 기준선 표기를 `feature/macOS-version@ce96203, app version 0.0.4+4`로 정정하고, 재검증 시 빌드 산출물 버전을 로그에 남긴다.

### 4.3 [P0] 회귀 비교의 비교가능성 결함 (가장 중요)

프롬프트·계획서의 핵심 전제는 "11-09에는 `audio=1`이었고 지금은 `audio=0`"이라는 회귀다. 그러나 11-09 근거를 확인한 결과:

- `20261109_macOS테스트결과보고서_v1.0.md`의 `CONFERENCE_OK (video=1 audio=1)`는 **UI 클라이언트가 아니라 `tool/conference_probe.dart`** 실행 결과다.
- 해당 프로브는 계정 **1102/1103/1104**, `remoteStreams=2`로 측정되었다.
- 현재 증상은 **UI 클라이언트(1101/1102/1103)** 에서 관측되었다.

즉 **측정 주체·계정·스트림 모델이 다른 두 결과를 회귀로 비교**하고 있다. "11-09 대비 회귀"라는 전제 자체가 성립하지 않을 수 있다.

**권고**:
1. 회귀 판정 전, **동일 도구(프로브 vs 프로브, 또는 UI vs UI)** 로 현재 상태를 재측정해 비교한다.
2. `conference_probe.dart`를 현재 HEAD로 재실행하여 `audio=1`이 재현되는지 확인 → 재현되면 **UI 클라이언트 계층 문제(H1) 강하게 지지**, 재현 안 되면 서버/환경 문제로 좁힌다.
3. 이 실험이 **가장 빠른 원인 분리**이므로 W3 앞에 배치할 것을 권고.

### 4.4 [P0] H1 측정지표 미정의

`remoteStreamAdded video=1 audio=0` 로그는 `media_provider.dart:242`에서 **개별 수신 스트림 단위**로 찍힌다. flutter_webrtc는 트랙별로 별도 스트림 이벤트를 줄 수 있으므로, 이 로그 한 줄만으로 "오디오 없음"을 확정할 수 없다. 계획서 §5.4는 "track 수 확인"을 언급하나 **판정 기준이 수치화되어 있지 않다.**

**권고 — 판정 지표 명시**:

| 지표 | 측정 위치 | "오디오 정상" 기준 |
|------|-----------|-------------------|
| audio-only 스트림 이벤트 수신 | `media_provider` remoteStreamAdded 로그 | ≥1 (또는 통합 스트림에 audio track 존재) |
| 원격 SDP `m=audio` | 클라이언트 remote description / 서버 pjsip logger | 존재 + `a=sendrecv` |
| audio RTP 수신량 | WebRTC `getStats()` `inbound-rtp/audio.bytesReceived` | 증가 추세 (>0 및 지속) |
| 실제 청취 | 사람 검증 | 양방향 가청 |

### 4.5 [P0] 의사결정 분기표 부재

계획서는 "확인 포인트"는 있으나 **증거 → 원인 → 조치**의 분기표가 없다. 아래 표를 §5에 추가할 것을 권고한다.

| 관측 결과 | 판정 | 다음 조치 |
|-----------|------|-----------|
| 서버/클라 SDP에 `m=audio` 없음 | H2 확정 | 서버 ConfBridge/PJSIP 협상 조사(F3) |
| `m=audio` 있으나 `a=inactive`/`recvonly` | H2 확정 | 재협상 타이밍/프로파일 조사(F3) |
| `m=audio` + `sendrecv`, 클라 audio track 0, RTP bytes 0 | H4(경로) | ICE/DTLS/RTP 디버그 |
| `m=audio` + `sendrecv`, RTP bytes 증가, 클라 track 0/렌더 없음 | H1 확정 | 클라이언트 수정(F2) |
| 프로브는 audio=1, UI는 audio=0 | H1 확정 | UI 클라이언트 계층 수정(F2) |

### 4.6 [P1] repo vs 런타임 diff 방법 결함

§5.2는 "repo 소스와 diff/md5 비교"를 지시하지만, `/etc/asterisk/pjsip.conf`는 **template + 환경변수 치환 결과물**이다. 템플릿의 `${SIP_PASSWORD_*}` 등이 치환되므로 raw diff/md5는 **항상 불일치**한다.

**권고**: `pjsip.conf`는 (a) 치환된 값 마스킹 후 구조 비교, 또는 (b) `asterisk -rx "pjsip show endpoint ..."` 런타임 출력과 템플릿을 항목별 대조. `confbridge.conf`/`extensions.conf`처럼 정적 파일만 md5 비교.

### 4.7 [P1] H2 우선순위 하향 검토

`video_mode=sfu`가 audio m-line을 삭제한다는 근거는 현재 없다. 계획서도 F3에서 인정하지만, 원인 가설 트리에서 H2를 P0로 두고 있다. **SDP 증거 확보 전까지 P1로 두고**, H1/H5 및 프로브 대조를 먼저 수행할 것을 권고.

### 4.8 [P1] 합격 기준 허점 (T2)

T2 합격 기준의 "수신 오디오 stats>0"은 **무음/오배선/한쪽만 들림도 통과**시킬 수 있다. 다음을 추가:
- 양방향 **실제 가청** 확인(사람 검증)
- RTCP 수신 손실률 임계(예: <2%)
- 3자 중 최소 2자 이상 발화 시 상호 청취

### 4.9 [P1] WBS·역할·브랜치

- 총 예상 "4~6시간"과 단계 합계가 불일치(단계 합 약 6~8h). 재산정 필요.
- 담당이 "권장"으로만 표기 → **RACI(실행/검증/승인)** 명시 권고.
- 계획서가 권장한 서버 작업 브랜치(`fix/confbridge-remote-audio`)가 아직 미생성. 착수 전 생성 여부 확인.

### 4.10 [P2] 로그 보안·보관

`pjsip set logger on`은 SIP 메시지에 인증 헤더/토큰을 포함할 수 있다. 증거 보관 시 **민감정보 마스킹 규칙**과 보관 기한/접근 제한을 명시할 것을 권고.

## 7. 권고 실행 순서 (수정안)

1. **S0 (신규·최우선)**: 프로브 재현 실험 — `conference_probe.dart`를 현재 HEAD로 실행해 `audio=1` 재현 여부 확인. UI/프로브 격차로 H1 vs H2를 즉시 분리.
2. **W1-W2**: 계정 통제 + 서버 런타임 기준선/구조 비교(정정된 방법).
3. **W3**: 최신 UI 클라이언트 3대 재검증(F1) + §4.4 지표 수집.
4. **W4**: SDP/RTP 캡처 → §4.5 분기표로 원인 확정.
5. **W5-W7**: 원인별 수정(F2 서버 확정 시 F3/F4) → 재검증 → 보고서.

## 8. 결론 및 승인 의견

1. **프롬프트 v1.0은 승인 불가(D).** 텍스트 손상과 기술 오류가 실행 신뢰성을 훼손한다. v1.1 재작성이 필수다.
2. **작업계획서 v1.0은 조건부 승인(B).** 골격·방향은 우수하나, (a) 기준선 버전, (b) 회귀 비교가능성, (c) 측정지표·분기표, (d) repo 비교 방법 4가지를 보완해야 한다.
3. **가장 큰 리스크는 "11-09 대비 회귀"라는 전제의 비교가능성 결함**이다. 프로브와 UI 클라이언트를 동일 조건으로 비교하기 전에는 서버 설정을 변경해서는 안 된다.
4. **가장 빠른 원인 분리는 프로브 재실험(S0)** 이다. 이를 WBS 최상단으로 이동할 것을 강력히 권고한다.

**판정: 조건부 승인 — §6 체크리스트 완료 후 착수 승인.**
