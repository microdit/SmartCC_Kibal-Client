## 1. 목적

v2.0/v2.1은 "증거 없이 서버 설정을 바꾸지 않는다"는 원칙 아래 H1(클라이언트)과 H2(서버 ConfBridge SDP)를 모두 열어두었다. 본 문서는 **신규 실측 로그**로 두 가설의 우선순위를 재판정하고, 다음 결정 실험과 잠재 수정 지점을 확정한다.

## 2. 입력 로그 요약

### 2.1 시간 정합

- 서버 로그는 **UTC**(`08:4x`), 클라이언트 로그는 **KST**(`17:4x`) — **+9시간** 오프셋. 이벤트 대응은 오프셋 적용 후 일치한다.
- 예: 서버 `08:47:06` 1102 ConfBridge 입장 ↔ 클라이언트 1102 `17:47:06` callPressed/`17:47:06.78` remoteStreamAdded.

### 2.2 참가 타임라인 (KST 기준)

| 시각 | 참가자 | 이벤트 |
|------|--------|--------|
| 17:40:43 | 1102 | 등록 완료(WS 8088) |
| 17:44:35~50 | 1103 | WS `No route to host(errno 65)` → 15s 타임아웃 실패 → **자동 재연결 성공**(17:44:50) |
| 17:47:06 | 1102 | 6000 입장(서버: ConfBridge, `conf-onlyperson.gsm` 재생) |
| 17:47:06.78 | 1102 | remote `video=1 audio=0` (streams=1) |
| 17:47:17 | 1103 | 6000 입장 |
| 17:47:17.28 | 1103 | remote `video=1 audio=0` (streams=1) |
| 17:47:17.60 | 1103 | local `video=2 audio=1` ← **비정상(로컬 video 트랙 중복)** |
| 17:47:18.17 | 1102 | remote `video=1 audio=0` (streams=2) |
| 17:47:39 | 1101 | 등록 완료(카메라 없음) |
| 17:47:45 | 1101 | 6000 입장, `voiceOnly=true`, local `video=0 audio=1` |
| 17:47:46.45 / .56 | 1101 | remote `video=1 audio=0` ×2 (streams=1→2) |

### 2.3 서버 로그 핵심

- 전 참가자 `softmix` base-bridge 합류, `confbridge-join.gsm` 재생.
- 각 채널에서 `res_rtp_asterisk`의 `Strict RTP learning ... remote address set to: 0.0.0.0:9` 라인 개수:
  - **1102: 2개** (2026-11-10 08:47:06, `0x...3e50`, `0x...2910`)
  - **1103: 2개** (08:47:17)
  - **1101: 1개** (08:47:45)
- `08:46:43` "Web socket closed abruptly" → AOR 1101 contact 제거("due to shutdown") → 08:47:39 재등록.

## 3. 확정 사실 (로그로 입증)

| ID | 사실 | 근거 |
|----|------|------|
| F1 | **Asterisk는 참가자별 오디오 RTP 인스턴스를 생성했다** | 1101은 카메라가 없어 `voiceOnly=true`(오디오만)로 호출했고, 서버 로그에 RTP 인스턴스가 **정확히 1개**만 생성됨 → 그 1개가 audio. 오디오 m-line이 협상되지 않았다면 인스턴스가 생성되지 않는다 |
| F2 | 1102/1103은 audio+video 2개 m-line으로 협상됨 | RTP 인스턴스 2개 |
| F3 | 그럼에도 3대 모두 원격 audio 트랙 0 | 클라이언트 `remoteStreamAdded ... audio=0`, 세션 누적 audio=0 |
| F4 | 원격 video 이벤트는 참가자 수에 따라 증가 | 1102: 1→2, 1101: 1→2 (참가자 증가 시점) |
| F5 | 1101(오디오 전용)조차 audio=0 | 로컬 장치/카메라 유무와 무관한 **전 클라이언트 공통** 현상 |
| F6 | 테스트 빌드는 v1.1 진단 로그 미포함 | 로그 포맷이 `streams=N video=.. audio=..`(구 포맷). `session(video=.., audio=..)` 신포맷 아님 → `0becb03` 이전 빌드로 시험됨 |

## 4. 가설 재평가

| ID | 가설 | v2.1 우선순위 | v2.2 재판정 | 근거 |
|----|------|---------------|-------------|------|
| **H2** | ConfBridge/PJSIP가 `m=audio` 누락/inactive | P1(증거대기) | **반증에 가까움(↓)** | F1: 오디오 전용 1101에 audio RTP 인스턴스 생성. 서버는 오디오를 협상·믹싱함. `conf-onlyperson.gsm` 등 브리지 오디오도 정상 |
| **H1** | 클라이언트가 수신 오디오 트랙을 매핑/노출하지 못함 | P0 | **최우선(P0↑)** | F1~F5: 서버 오디오 존재 + 클라 전원 audio=0 + 클라 계층 단일 원인 |
| **H4** | ICE/DTLS/RTP 경로 문제로 오디오 미수신 | P1 | **P1(검증 필요)** | `0.0.0.0:9`는 ICE 학습 전 정상 초기값. video가 실제 재생된다면 BUNDLE 동일 전송로이므로 오디오만 미수신은 설명 약함. 단 getStats로 확증 필요 |
| H3 | dialplan/endpoint 속성 | P1 | **반증** | dialplan/Answer 정상 실행, 1101 오디오 인스턴스 생성 |
| H5 | 계정 혼선 | P0(통제) | **통제됨** | 1101/1102/1103 각각 정상 등록(중복 아님). 단 1103 초기 연결 실패 이력 있음 |

**핵심 전환**: F1이 H2를 사실상 무력화한다. 문제는 **서버가 오디오를 보내지 않는 것이 아니라, 클라이언트가 받은 오디오를 드러내지 못하는 것**으로 좁혀진다.

## 5. 신규 발견 결함·이상 징후

| ID | 내용 | 판정 | 조치 |
|----|------|------|------|
| A1 | `sip_ua`의 `onTrack`은 `event.streams.isNotEmpty`일 때만 STREAM 이벤트를 emit한다(`rtc_session.dart:1749`). **msid가 없는 원격 오디오 트랙은 `event.streams`가 비어 조용히 폐기**될 수 있다 | **H1의 구체적 메커니즘 후보(최유력)** | 원격 SDP의 audio `a=msid` 유무 확인 + `onTrack` 래핑/수신기 기반 복구 |
| A2 | 로컬 `video=2` (1103/1102, 재협상 시점) — 카메라 보유 기기에서 **로컬 video 트랙 중복** | 클라이언트 결함 | 재협상 시 트랙 누적 로직 점검(오디오 협상에도 영향 가능) |
| A3 | 1102 단독 상태(참가자 0명)에서도 `remote video=1` 수신 | 측정 함정 | "video 트랙 존재"는 실제 영상 수신 증거가 아님(SFU가 비활성 video m-line을 협상). **getStats bytes로 판정해야 함** |
| A4 | 1101 `Web socket closed abruptly` → contact "due to shutdown" → 재등록 | D8 재현 | 테스트 전 등록 안정화, 재등록 완료 후 호출 |
| A5 | 1103 초기 `No route to host`(15s 실패) → 자동 복구 | 네트워크/D8 | 테스트 시작 전 연결 상태 확인 |
| A6 | 로그 포맷이 구버전 | 검증 공백 | `0becb03` 이후 빌드로 재시험해야 세션 누적/스트림 구분 지표 확보 |

## 6. 코드 근거 (A1 상세)

`sip_ua 1.1.0` `rtc_session.dart` unified-plan 분기:

```dart
_connection!.onTrack = (RTCTrackEvent event) {
  if (event.streams.isNotEmpty) {
    emit(EventStream(session: this, originator: Originator.remote,
                     stream: event.streams[0]));
  }
};
```

- 원격 오디오 트랙에 `a=msid`가 없으면 `event.streams`가 비어 **STREAM 이벤트 자체가 발생하지 않는다.**
- 그 결과 UI의 `remoteStreamAdded`에 audio 이벤트가 한 번도 나타나지 않으며, `MediaManager`는 오디오 스트림을 보관할 기회를 얻지 못한다. → F3~F5와 정확히 일치.
- 반면 SFU video 트랙은 msid를 동반해 정상 emit → F4와 일치.

> 주의: 이 메커니즘은 **가장 유력한 후보**이며, 원격 SDP의 `m=audio` `a=msid` 확인과 `getStats()`로 최종 확정해야 한다(아래 §7).

## 7. 다음 결정 실험 (최소·우선순위)

| ID | 실험 | 합격/판정 기준 | 목적 |
|----|------|----------------|------|
| **T-A** | `0becb03` 이후 빌드로 3대 재시험 | 세션 누적 `session(video, audio)` 및 `sessionAudio` 확인 | A6 해소, H1 지표 확보 |
| **T-B** | 서버 `rtp set debug on` + `pjsip show channelstats` (3자 유지 중) | 1101 채널의 audio `Rx/Tx` 패킷 증가 여부 | H4 vs H1 분리 (오디오 RTP가 실제 흐르는가) |
| **T-C** | 클라이언트 `getStats()` `inbound-rtp/audio.bytesReceived` 로그 1줄 추가 | 0 증가=H4, 증가=H1(매핑) | 원인 확정 |
| **T-D** | 원격 SDP 저장 로그(`EventSdp`/`pc.remoteDescription`) | audio `m=` 존재·direction·`a=msid` 유무 | A1 확정 |
| T-E | `conference_probe.dart` 재실행 (v2.1 S0) | 프로브 audio=1 여부 | 11-09 회귀 비교가능성 확보 |

**판정 분기**:
- T-B/T-C에서 오디오 RTP bytes **증가 + 트랙 미노출** → **H1(A1) 확정** → 클라이언트 수정(F2).
- 오디오 RTP bytes **0** → **H4** → ICE/DTLS/BUNDLE 조사(F3 성격).
- H2는 T-B에서 오디오 RTP 인스턴스/스트림이 확인된 시점에 **종결**.

## 8. 잠재 수정안 (H1 확정 시)

### 8.1 [권장] `onTrack` 래핑으로 msid 없는 오디오 트랙 복구

`EventPeerConnection` 수신 시 sip_ua가 설치한 핸들러를 보존하고 래핑한다(개념 스케치):

```dart
// sip_ua가 emit하는 EventPeerConnection을 구독
final prev = pc.onTrack;
pc.onTrack = (RTCTrackEvent e) {
  if (e.streams.isEmpty && e.track.kind == 'audio') {
    // msid 없는 원격 오디오 트랙 → 세션 스트림으로 승격
    _promoteOrphanAudioTrack(e.track); // 신규 MediaStream에 addTrack 후 MediaManager.addRemoteStream
  }
  prev?.call(e); // streams.isNotEmpty인 경우만 sip_ua가 emit하므로 중복 없음
};
```

- **검증 필수**: 이전 `addTrack` nil 크래시(D8)는 "재협상으로 nil이 된 기존 스트림"에 추가할 때 발생했다. **신규 스트림 생성 + 영속 보관** 방식으로 회피 가능한지 실측 확인.
- 대안: `pc.getReceivers()`에서 `kind=='audio'` 트랙을 찾아 세션 스트림에 연결.

### 8.2 보조 수정

- **A2**: 재협상(re-INVITE) 시 로컬 `video` 트랙 중복 방지(트랙 ID 기준 dedupe, `_localMediaStream` 재사용).
- **A3**: T2 합격 기준에서 "track 존재"를 제거하고 **`getStats()` bytes 증가**로 대체.

### 8.3 서버 측

- 현 로그 기준 **서버 설정 변경 필요성 없음**. `video_mode=none` A/B는 **불필요**(F1로 H2 반증). H4로 판정될 때만 ICE/`rtp.conf`/BUNDLE 조사.

## 9. 문서·계획 반영 권고 (v1.2)

1. v2.1 §6.3 분기표에 **"서버 오디오 RTP 인스턴스 존재 + 클라 audio=0 → H1"** 행 추가.
2. 계획서 v1.1 §5.4에 T-B/T-C/T-D를 **W4 필수 증거**로 추가.
3. H2를 "증거대기"에서 **"현 로그로 반증됨(재개 조건: T-B에서 서버 오디오 스트림 부재 확인 시)"**으로 명시.
4. 프롬프트/계획서의 `video_mode` A/B 항목 삭제 또는 "H4 확정 시에만"으로 축소.
5. 테스트 기준선을 **`0becb03` 이후 빌드**로 고정(A6).
6. `conference_probe.dart`(S0)를 T-E로 유지하되, UI 원인 확정의 **주 증거는 T-B/T-C**임을 명확화.

## 10. 결론

- **H2(서버가 `m=audio`를 누락)는 현 로그로 사실상 반증**되었다. 1101(오디오 전용) 채널에 오디오 RTP 인스턴스가 생성되었고, 서버는 오디오를 정상 협상·믹싱한다.
- **H1(클라이언트가 원격 오디오 트랙을 노출/매핑하지 못함)이 최우선 원인**이다. `sip_ua`의 `onTrack`이 `event.streams`가 비어 있으면 이벤트를 버리는 구조(A1)가 로그와 정확히 일치한다.
- 확정을 위해 **T-B(서버 오디오 RTP) + T-C(클라 getStats)** 를 최우선 실행하고, `0becb03` 이후 빌드로 재시험해야 한다.
- 서버 설정 변경은 **현 시점 불필요**하며, `video_mode=none` A/B는 수행하지 말 것을 권고한다.

**v2.2 판정: 원인은 서버가 아니라 클라이언트 원격 오디오 트랙 매핑(H1/A1). T-B·T-C로 확정 후 클라이언트 수정(F2) 직행.**
