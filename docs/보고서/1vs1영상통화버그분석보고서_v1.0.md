## 1. 사용자 보고 증상

- 1:1 영상통화를 걸면 **연결(통화 화면 진입)은 되지만 실제 영상통화가 이루어지지 않는다**
- 상대방 영상이 나오지 않고, 상대방에게도 내 영상이 보이지 않는다
- 다자간 회의(6000)와 달리 re-INVITE/ICE 실패 로그 없이 "조용히" 영상만 없음

## 3. 원인 분석

### 3.1 [V1·확정·근본] 수신 INVITE의 video 플래그 미설정 — 모든 수신 전화가 voiceOnly=true

**코드 경로**

1. `packages/sip_ua/lib/src/rtc_session.dart:364` `init_incoming()` — 수신 INVITE 처리 시 `data = options['data'] ?? data;` 만 수행하고 **`data['video']`를 설정하지 않는다**.
   - 비교: 발신 `connect()`(`rtc_session.dart:264`)에는 `data?['video'] = !(options['mediaConstraints']['video'] == false);`가 있다.
2. `packages/sip_ua/lib/src/sip_ua_helper.dart:250`:
   ```dart
   bool hasVideo = session.data?['video'] ?? false;
   _calls[event.id] = Call(event.id, session, CallStateEnum.CALL_INITIATION, !hasVideo);
   ```
   → 수신 전화는 offer SDP에 영상이 있어도 **`Call.voiceOnly = true`로 고정**.

**영향**: 이후 모든 수신 통화 판정이 "음성 전화"로 오인된다.

### 3.2 [V2·확정·근본] 수신 측 answer가 항상 오디오-only

**코드 경로**

`macos-client/lib/src/sip/sip_client.dart:323`:

```dart
final voiceOnly = call.voiceOnly || !await _canUseVideo(mediaStream);
call.answer(_helper.buildCallOptions(voiceOnly), mediaStream: mediaStream);
```

- V1 때문에 `call.voiceOnly`가 항상 true → `voiceOnly=true` → `buildCallOptions(true)`는 `mediaConstraints['video']=false`, `OfferToReceiveVideo=false`를 만든다.
- 결과: 수신 측의 200 OK answer에 **영상 m-line이 없거나 비활성** → Asterisk는 오디오만 브리지 → **양쪽 모두 상대 영상을 받을 수 없다**.
- 발신 측 offer에 영상이 포함되어 있어도 answer가 오디오-only면 영상은 성립하지 않는다.

**이것이 "연결은 되지만 영상통화가 안 되는" 직접 원인이다.**

### 3.3 [V3·확정] v0.0.13까지는 수락 자체가 크래시로 실패 (기존 B2)

| 크래시 | 위치 | 결과 |
|--------|------|------|
| `Navigator.of` Null | `lib/app.dart:80` — `MaterialApp.router` 위의 context로 Navigator 호출 | 수신 다이얼로그 닫기 실패 |
| `Concurrent modification during iteration` | `packages/sip_ua/lib/src/rtc_session.dart:557-563` — answer의 video=false 처리가 내부 리스트를 순회하며 `removeTrack` | answer 미완료 → 발신 603 / 수신 487 |

- v0.0.14에서 F2(루트 네비게이터 키 사용)·F3(복사본 순회)로 **수정 완료**.
- 단, 크래시가 사라져도 V1/V2가 남아 있으면 **정상 수락 + 오디오-only 통화**가 된다.

### 3.4 [V4·잔여 위험] voiceOnly 수락 시 공유 로컬 스트림의 video track 제거

`rtc_session.dart:563-568` (answer 경로):

```dart
if (mediaStream != null && mediaConstraints['video'] == false) {
  tracks = mediaStream.getVideoTracks().toList(); // v0.0.14: 복사본 순회로 크래시만 방지
  for (MediaStreamTrack track in tracks) {
    mediaStream.removeTrack(track);               // ← 앱 공유 로컬 스트림 자체를 변경
  }
}
```

- `mediaStream`은 `MediaProvider`가 관리하는 **앱 공유 로컬 스트림**이다. 여기서 video track이 제거되면 수신자의 **셀프 카메라 프리뷰도 사라진다**.
- V1이 수정되면 영상 전화에서는 이 분기를 타지 않지만, 음성-only 수락 경로에서는 여전히 위험하다.
- v1.6 테스트의 "셀프카메라 타일 영상이 사라짐" 증상과 관련 가능성이 있어 별도 확인이 필요하다.

### 3.5 [N1·운영] 1101 → 1102 404

- 17:33:47 시점 1102는 서버에서 Unreachable/등록 해제 상태였다(다자간 보고서 N1의 Wi-Fi 품질 문제와 동일 계열).
- 앱 결함이 아니며, 네트워크/등록 상태 개선 후 재시도가 필요하다.

## 5. 해결 방안

### 5.1 [P0] F-A: 수신 측 voiceOnly 판정을 실제 offer SDP 기준으로 변경

`sip_client.dart`의 `answer()`에서 `call.voiceOnly` 대신 **수신 SDP의 영상 m-line 존재 여부**를 사용한다.

```dart
// 기존
final voiceOnly = call.voiceOnly || !await _canUseVideo(mediaStream);

// 수정안
final peerOffersVideo = call.remote_has_video; // sip_ua Call의 기존 getter (수신 INVITE SDP 파싱)
final voiceOnly = !peerOffersVideo || !await _canUseVideo(mediaStream);
```

- `Call.remote_has_video`(`sip_ua_helper.dart:687`)는 이미 구현되어 있으며, 수신 INVITE의 SDP에서 `m=video`를 파싱한다.
- 장점: 포크 수정 없이 앱 레벨에서 최소 변경.

### 5.2 [P0·병행 권장] F-B: 포크에서 수신 세션의 video 플래그 정상화

`packages/sip_ua/lib/src/rtc_session.dart`의 answer 경로에서 offer SDP를 이미 파싱해 `peerHasVideoLine`을 계산한다(546행 부근). 이를 세션 데이터에 반영한다.

```dart
// answer() 내 offer SDP 파싱 직후
data?['video'] = peerHasVideoLine;
```

- `sip_ua_helper`의 `EventNewRTCSession` 시점에는 answer 전이라 SDP 파싱이 아직 안 되어 있다. 실제로는 `_receiveInvite`에서 request SDP를 파싱하는 시점이 더 이르므로, 해당 시점에 `session.data['video']`를 설정하면 `Call.voiceOnly`와 수신 UI("영상 전화" 표시)까지 함께 정상화된다.
- F-A만으로도 1:1 영상은 성립하지만, 수신 다이얼로그의 영상/음성 구분 표시까지 고치려면 F-B가 필요하다.

### 5.3 [P1] F-C: voiceOnly 수락 시 공유 스트림 변경 금지

- `rtc_session.dart`의 트랙 제거 루프가 앱 공유 `mediaStream`을 직접 변경하지 않도록 한다.
- 방안: answer에 사용할 스트림의 **복사본을 만들어 트랙을 제거**하거나, 트랙 제거 대신 **answer constraints와 direction(recvonly/inactive)만으로** 제어한다.
- v0.0.14의 복사본 순회 수정은 크래시 방지일 뿐 스트림 변경 자체는 남아 있다.

### 5.4 [운영] N1: 등록 상태 확인

- 1:1 시도 전 양 단말이 `registered`인지 확인(404 방지). 1102/1103은 유선 또는 5GHz Wi-Fi 권장.

## 7. 다자간(6000) 작업과의 관계

- 1:1과 다자간은 **원인이 다르다**. 다자간은 ConfBridge SFU의 re-INVITE/SFU 트랙 관리 문제(별도 작업 진행 중), 1:1은 **수신 answer의 영상 제외** 문제다.
- 다자간 화면(`/conference`) 작업과 1:1 화면(`/call`)은 분리되어 있으므로, 본 수정은 1:1 경로에 한정된다.
- 단, `media_manager`의 원격 스트림/트랙 파이프라인(F4 등)은 공유하므로, 다자간 작업 완료 후 1:1도 함께 회귀 검증한다.
