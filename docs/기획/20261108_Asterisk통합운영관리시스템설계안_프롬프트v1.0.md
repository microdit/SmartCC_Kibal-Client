# 0. AI Agent 역할 및 최종 목표

너는 Asterisk, PJSIP, SIP, AMI, ARI, Docker, Backend, Web UI, Monitoring, DevOps, 보안 분야의 수석 아키텍트이자 구현 담당 개발자다.

현재 SmartCC Kibal 프로젝트에 Asterisk PBX 운영을 위한 독립적인 Operations Management Platform을 추가한다.

이 시스템은 단순한 상태 조회 화면이 아니다.

실제 운영자가 Asterisk 서버를 관리하고, SIP 계정을 생성하고, 통화 상태를 확인하고, 장애를 분석하고, 설정을 변경하고, 안전한 운영 명령을 실행할 수 있는 통합 운영 플랫폼이어야 한다.

다음 4개 핵심 영역을 반드시 구현한다.

1. Monitoring
2. Administration
3. Operations Console
4. Incident & Audit

설계 문서만 작성하고 종료하지 않는다.

기존 소스 분석 → 상세 설계 → 코드 구현 → 실행 → 테스트 → 오류 수정 → 결과 보고까지 수행한다.

단, 기존 서비스에 영향을 주는 작업은 사전 확인과 승인 절차를 준수한다.

## 2.2 인터페이스별 역할 분리

### AMI

기본 운영 인터페이스로 사용한다.

사용 목적:

- Asterisk 상태 조회
- Endpoint 상태
- Channel 상태
- Queue 상태
- 통화 이벤트
- 통화 제어
- CLI 명령 실행이 필요한 제한된 운영 작업

### ARI

고급 통신 애플리케이션 제어가 필요한 경우 사용한다.

사용 목적:

- Channel 제어
- Bridge 관리
- Stasis 이벤트
- 통화 흐름 제어
- 고급 미디어 제어

ARI를 단순한 상태 조회를 위해 무조건 도입하지 않는다.

### CLI

진단과 제한된 관리 명령에 사용한다.

웹 화면에서 임의의 Shell 명령을 실행하지 않는다.

### CDR / CEL

- CDR: 완료된 통화의 요약 정보
- CEL: 채널 및 통화 흐름 이벤트

두 데이터를 분리하여 관리한다.

### Metrics / Logs

AMI 이벤트만으로 모든 서버 상태를 판단하지 않는다.

주기적 Snapshot, Metrics, Logs, AMI 이벤트를 결합한다.

# 5. Asterisk Connector 구현

운영관리 Backend에 Asterisk Connector 계층을 구현한다.

## 5.1 AMI Connector

요구사항:

- 지속적인 AMI 연결
- Login
- Event 수신
- Action 실행
- Response 처리
- Connection Health Check
- 자동 재연결
- Timeout 처리
- Error Handling
- Event Parsing
- Event Deduplication
- Connection Status

연결 장애가 발생하면 재연결을 수행한다.

재연결 이후에는 현재 상태를 Snapshot으로 다시 조회한다.

AMI 이벤트가 중복되거나 순서가 뒤바뀔 가능성을 고려한다.

## 5.2 AMI 권한

AMI 계정은 운영관리 전용으로 분리한다.

다음 원칙을 적용한다.

- 관리자 계정과 AMI 계정 분리
- 읽기와 쓰기 권한 분리
- 명령 권한 최소화
- 접속 IP 제한
- 내부 네트워크 접근
- TLS 또는 보호된 네트워크 사용
- Secret 외부 노출 금지

AMI의 `command` 권한은 강력한 권한이므로 무분별하게 부여하지 않는다.

필요한 이벤트 및 Action만 허용하도록 설계한다.

## 5.3 ARI Connector

ARI가 필요한 기능에 한해 구현한다.

- REST API Client
- WebSocket Event Client
- Connection Management
- Authentication
- Timeout
- Retry
- Event Processing

ARI를 브라우저에서 직접 호출하지 않는다.

반드시 Operations Backend를 통해 접근한다.

## 5.4 Multi-Instance 지원

초기에는 기존 Asterisk 한 대를 대상으로 구현한다.

다만 데이터 모델과 Backend 구조는 여러 Asterisk Instance를 추가할 수 있도록 설계한다.

각 Instance는 독립적인 연결 정보와 상태를 갖는다.

# 7. Operations Console 구현

운영자가 Asterisk 명령을 실행하는 독립 화면을 구현한다.

## 7.1 Command Catalog

다음과 같은 명령을 우선 등록한다.

### READ

- core show version
- core show uptime
- core show channels
- core show channels count
- core show calls
- pjsip show endpoints
- pjsip show registrations
- pjsip show contacts
- pjsip show transports
- pjsip show endpoint {endpoint}
- pjsip show aor {aor}
- dialplan show
- core show settings

### DIAGNOSTIC

- pjsip set logger on
- pjsip set logger off
- core set verbose {level}
- core set debug {level}

진단 명령은 지속 실행으로 인한 로그 폭증을 막기 위해 자동 종료 또는 시간 제한을 구현한다.

### CHANGE

- pjsip reload
- dialplan reload
- core reload

실제 지원 명령과 모듈 상태를 검증한다.

### CRITICAL

- core restart now
- core restart gracefully

위험 작업은 별도 승인과 재인증을 요구한다.

실제 지원되지 않는 명령을 임의로 등록하지 않는다.

## 7.2 Command Execution Security

임의의 Shell 실행을 허용하지 않는다.

다음 명령은 웹 콘솔에서 실행할 수 없도록 한다.

- bash
- sh
- rm
- kill
- docker
- docker exec
- 임의 경로 접근
- 임의 스크립트 실행

명령은 미리 등록된 Command Catalog에서만 선택한다.

파라미터는 명령별 Schema로 검증한다.

명령 실행 결과에는 다음을 기록한다.

- operator
- instance
- command_id
- parameters
- start_time
- end_time
- result
- exit_status
- output_summary
- approval_id

민감한 출력은 마스킹한다.

# 8. Configuration Management 구현

설정 관리 기능은 반드시 안전한 변경 절차를 사용한다.

## 8.1 설정 원본 관리

현재 Docker 구성과 실제 설정 경로를 분석한다.

운영 설정의 Source of Truth를 지정한다.

컨테이너 내부 파일만 수정하는 방식은 사용하지 않는다.

호스트 설정 파일, 지정된 설정 저장소 또는 관리 가능한 영구 볼륨을 사용한다.

## 8.2 Configuration Lifecycle

다음 순서를 강제한다.

1. Read Current
2. Edit
3. Generate Candidate
4. Diff
5. Validate
6. Approve
7. Backup
8. Apply
9. Verify
10. Rollback if failed

## 8.3 Configuration Validation

다음을 검증한다.

- Syntax
- Duplicate Object
- Missing Reference
- Invalid Parameter
- Invalid Transport
- Endpoint/AOR/Auth Relationship
- Context Reference
- Environment Variable
- Secret Reference

실제 Asterisk 버전에 적합한 검증 방법을 사용한다.

## 8.4 Apply Policy

설정 종류별로 적용 방식을 구분한다.

- Reload
- Module Reload
- Dialplan Reload
- Restart Required

설정 적용이 통화 중인 채널에 영향을 줄 수 있는지 사전에 판단한다.

영향 범위를 운영자에게 표시한다.

적용 후 실제 실행 설정과 관리 시스템의 설정 원본이 일치하는지 확인한다.

# 9. SIP Administration 구현

## 9.1 Endpoint 관리

CRUD 기능을 구현한다.

- 생성
- 조회
- 수정
- 비활성화
- 삭제

Endpoint, Auth, AOR의 관계를 명확하게 관리한다.

## 9.2 인증 관리

SIP Digest 인증의 원리를 준수한다.

- username
- realm
- auth_type
- password
- md5_cred

Asterisk 버전과 설정 형식을 확인한 뒤 구현한다.

MD5(password)를 `md5_cred`에 임의로 넣지 않는다.

비밀번호는 저장 시 안전하게 보호하고 원문 조회 기능을 제공하지 않는다.

## 9.3 기존 SIP 계정 보호

현재 존재하는 SIP 계정은 자동으로 재생성하거나 변경하지 않는다.

초기에는 조회 기능부터 구현한다.

계정 변경은 별도 승인 후 진행한다.

# 17. Docker 및 배포

기존 Docker Compose를 먼저 분석한다.

추가 검토 서비스:

- ops-backend
- ops-frontend
- prometheus
- grafana
- loki
- alertmanager
- node-exporter
- cadvisor
- ops-db (기존 DB 재사용이 불가능한 경우에만)

모든 서비스가 반드시 개별 컨테이너일 필요는 없다.

실제 운영 복잡도와 자원 사용량을 비교해 결정한다.

AMI 5038과 ARI 8088은 외부 공개 포트로 추가하지 않는다.

기존 Asterisk의 SIP, RTP, WebSocket 포트와 충돌하지 않도록 한다.

개발환경과 운영환경의 Compose 설정을 분리한다.
