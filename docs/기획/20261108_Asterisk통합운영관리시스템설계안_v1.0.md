SmartCC Kibal – Asterisk 통합 운영관리 시스템 설계안
제 의견은 Asterisk를 단순한 SIP 서버로 운영하지 말고, 별도의 PBX 운영관리 플랫폼(PBX Operations Management Platform)으로 관리하는 것입니다.

지금까지 진행한 SmartCC Kibal의 Flutter + LiveKit 화상회의 개발과도 분리된 독립 모듈로 설계하는 것이 좋겠습니다.

특히 Asterisk 운영에는 단순한 관리자 화면만으로는 부족합니다. 실제 운영자가 서버 상태를 확인하고, SIP 계정을 관리하고, 장애를 분석하고, 통화를 추적하고, 설정을 변경하고, 필요한 명령을 실행할 수 있어야 합니다.

따라서 다음 4개 영역을 하나의 운영관리 시스템으로 통합하는 방식을 제안합니다.
1. Monitoring – 서버 및 통신 상태 실시간 모니터링
2. Administration – Asterisk 설정 및 계정 관리
3. Operations Console – Asterisk CLI 및 운영 명령 실행
4. Incident & Audit – 장애 분석, 이벤트 이력, 관리자 작업 추적
이 시스템은 Flutter 클라이언트와 별도로 운영되는 웹 기반 관리자 플랫폼으로 만드는 것이 적절합니다.

- CLI는 진단과 제한된 운영 명령에 사용합니다.
- 설정 변경은 검증, 승인, 백업, 적용, 롤백 절차를 거칩니다.
- 운영자 계정과 SIP 사용자 계정은 별도로 관리합니다.

2.4 Asterisk 설정 관리
설정 관리가 이 시스템에서 가장 주의해야 할 부분입니다.

단순히 웹 화면에서 pjsip.conf를 편집하고 저장하는 방식은 위험합니다.

다음 절차를 강제하는 것을 권장합니다.
Configuration Lifecycle
1. 설정 조회
   
   현재 실행 중인 설정과 관리 시스템의 설정 원본 확인
2. 설정 편집
   
   GUI 폼 또는 고급 설정 편집기에서 수정
3. Diff 확인
   
   변경 전후 차이와 영향 범위 표시
4. Validate
   
   설정 문법, 필수 값, 중복 객체, 참조 관계 검증
5. 승인
   
   위험 작업은 별도 승인
6. Backup
   
   변경 전 설정 백업 및 버전 생성
7. Apply
   
   Reload 또는 Restart 중 적절한 적용 방법 실행
8. Verify / Rollback
   
   실제 적용 상태 확인 및 실패 시 이전 버전 복원

설정은 다음과 같이 분류합니다.
설정	관리 방식	적용 방식
PJSIP Endpoint	GUI + 파일/템플릿	지원되는 Reload
AOR / Auth	GUI + 파일/템플릿	지원되는 Reload
SIP Transport	고급 설정	재시작 필요 여부 검증
Dialplan	GUI + 파일	Dialplan Reload
RTP	고급 설정	적용 범위에 따라 Reload/Restart
Manager	제한된 관리자 설정	보안 검증 후 적용
ARI	제한된 관리자 설정	설정 검증 후 적용

실제 적용 방식은 사용 중인 Asterisk 버전과 모듈별 동작을 확인해서 결정해야 합니다.
2.5 Operations Console 설계
운영자가 Asterisk CLI 명령을 실행할 수 있는 화면입니다.

예를 들어 다음 명령을 실행할 수 있어야 합니다.
명령	용도	위험도
core show version	버전 확인	낮음
core show uptime	가동 시간	낮음
core show channels	통화 채널 확인	낮음
pjsip show endpoints	Endpoint 목록	낮음
pjsip show registrations	등록 상태 확인	낮음
pjsip show contacts	Contact 확인	낮음
pjsip show transports	Transport 확인	낮음
pjsip show logger on	SIP 패킷 추적 활성화	중간
dialplan show	Dialplan 확인	낮음
core reload	전체 Reload	높음
core restart now	서버 재시작	매우 높음

여기서 중요한 보안 원칙이 있습니다.

웹 콘솔에서 임의의 Shell 명령을 실행하도록 구현하지 않습니다.

CLI 명령도 허용 목록(Allowlist) 기반으로 실행하고, 명령별 권한 및 위험도를 적용합니다.

예를 들어 다음과 같이 구분합니다.
- READ_ONLY: 조회 명령
- OPERATOR: 제한된 통화 제어 및 진단
- ADMIN: 설정 변경 및 Reload
- SUPER_ADMIN: 서버 재시작, 위험 작업 승인
임의의 bash, sh, docker exec, rm, kill 명령은 운영 콘솔에서 실행할 수 없도록 합니다.

AMI의 command 권한 역시 CLI 실행 권한을 포함하므로, AMI 계정에 무제한 권한을 부여하면 안 됩니다.

2.6 통화 및 SIP 관리
통화 운영은 단순한 CDR 조회를 넘어 실시간 통화 추적이 필요합니다.

필수 기능:
- 현재 통화 중인 사용자
- 발신 번호 / 수신 번호
- 통화 시작 시각
- 통화 지속 시간
- Channel ID
- Linked ID
- SIP Call-ID(수집 가능한 경우)
- 통화 상태
- 종료 원인
- Hangup Cause
- 통화 종료 이벤트
- SIP 오류 응답
- RTP 통계
CDR은 완료된 통화의 요약 기록, CEL은 채널 및 통화 흐름 이벤트 추적에 활용합니다. 이 둘을 동일한 데이터로 취급하지 않아야 합니다.

통화 강제 종료는 운영자 권한이 있는 경우에만 제공하고, 실행 전 대상 채널과 영향 범위를 확인하게 합니다.

2.8 관리자 및 감사 로그

- 로그인 / 로그아웃

- 명령 실행

Asterisk 연결은 단일 Backend 프로세스가 모든 요청마다 새 AMI 연결을 생성하는 방식이 아니라, 장기 연결을 유지하는 Connector를 두는 것이 좋습니다.
- AMI 연결 상태 감시
- 자동 재연결
- 이벤트 중복 처리 방지
- 이벤트 순서 및 시간 기록
- 재연결 후 현재 상태 재조회
- 연결 장애와 실제 Asterisk 장애 구분
이벤트는 유실될 수 있으므로, AMI 이벤트만을 유일한 상태 저장 근거로 삼지 않습니다. 주기적인 Snapshot과 이벤트를 결합합니다.

4.4 운영 명령 실행 정책
명령 실행 기능은 다음 4단계로 나눕니다.
위험도	예시	정책
READ	상태·목록 조회	권한 확인 후 즉시 실행
DIAGNOSTIC	SIP Logger, 상세 진단	실행 시간 제한 및 자동 종료
CHANGE	Reload, 설정 적용	사전 검증 및 변경 이력
CRITICAL	Restart, 서비스 중단	재인증 및 별도 승인

여기서 core set verbose, pjsip set logger on처럼 진단 모드가 지속되는 명령은 실행 시간과 자동 종료를 반드시 관리해야 합니다.

또한 명령 실행은 다음 정보를 보관합니다.
- 요청자
- 대상 Asterisk 인스턴스
- 명령 ID
- 실행 인자
- 시작/종료 시각
- 종료 코드
- 결과 요약
- 표준 출력 및 오류 출력
- 승인자
- 실행 전후 상태
4.5 설정 변경 안전성
운영 시스템에서 설정을 변경할 때는 Asterisk 컨테이너 내부의 실행 파일만 수정하는 방식으로 구현하지 않습니다.

특히 현재 SmartCC Kibal의 Docker 기반 Asterisk 환경에서는 다음을 기준으로 합니다.
1. 호스트 또는 지정된 설정 저장소가 설정의 원본(Source of Truth)이 된다.
2. 템플릿과 환경변수의 역할을 분리한다.
3. Secret은 별도 보안 저장소 또는 제한된 환경변수로 관리한다.
4. 변경된 설정을 임시 경로에 생성한다.
5. 실제 Asterisk 버전과 설정 형식에 맞게 검증한다.
6. 적용 전에 백업과 Diff를 만든다.
7. 적용 방법을 선택하고 결과를 확인한다.
8. 실패하면 이전 설정으로 복구한다.
docker exec로 파일을 직접 수정하거나, 운영관리 화면에서 컨테이너 내부에 임의의 파일을 쓰는 기능은 기본 설계에서 제외합니다.
