1. 영속 반영(재생성 시 초기화) 운영 방식
- 지금 구현은 Ops DB 변경을 Asterisk *런타임(/run/asterisk)*에 즉시 반영(res_pjsip/회의실 reload)하지만, 컨테이너 재생성 시 pjsip.conf.template + env(SIP_PASSWORD_*) 기준으로 다시 생성되어 런타임 변경이 사라집니다.
- 사용자 의도(이해): 이를 수동 env 수정/재생성으로 운영하지 말고, 콘솔 OPS의 “Asterisk CLI”(또는 서비스 관련) 메뉴에서 실행 가능한 작업으로 추가해 변경 내용을 서비스에 영속적으로 반영되게 하자. 즉, Ops 화면에서 버튼/명령 한 번으로 “현재(또는 저장된) 설정을 서비스에 반영·유지”되도록 운영 흐름을 제공하려는 것으로 이해했습니다.
2. 클라이언트 인증 키(OPS_CLIENT_KEY)
- 사용자 의도(이해): OPS_CLIENT_KEY는 빌드 내장/공유값으로 두지 말고, macOS 클라이언트 사용자가 직접 키를 입력하게 한다. 클라이언트는 이 키로 인증된 상태에서 서버 연락처/접속 정보를 가져온다.
- 별도 관리 메뉴는 만들지 않는다. 대신 연락처의 해당 내선번호 항목에 ‘키 관리’ 필드를 추가해, 그 내선(연락처) 정보와 함께 같은 화면/데이터로 관리한다.
- (확인 포인트로 이해) 현재 OPS_CLIENT_KEY는 서버 전역(공유) 개념인데, 이를 내선별 항목으로 관리하겠다는 의미로 받아들였습니다. 즉 “어느 내선/연락처가 어떤 키로 인증·동기화되는지”를 연락처 단위로 관리하려는 취지로 이해했습니다.
3. SIP 비밀번호(연락처 비밀번호) 처리
- 사용자 의도(이해): SIP 비밀번호는 Ops 연락처에 저장된 값을 기준으로 하며, 클라이언트가 (입력한 키로) 인증되면 이를 자동으로 받아 갱신/사용해도 무방하다. 
- 즉, 비밀번호는 연락처 정보의 일부로 서버(Ops/Asterisk)에서 관리·변경되고 클라이언트는 이를 동기화해 “바로 접속”하는 구조로, 연락처 단위로 함께 관리되는 별도(동기화 대상) 자격정보로 이해했습니다. (클라이언트가 임의로 따로 들고 있는 값이 아니라 서버 연락처 값이 기준)
요약하면, “Ops 웹(연락처 단위로 키·비밀번호 관리)에서 수정 → Ops 메뉴(Asterisk CLI/서비스) 동작으로 Asterisk에 영속 반영 → 사용자가 키를 입력한 클라이언트가 연락처/비밀번호를 자동 동기화 받아 바로 접속” 흐름으로 만들라는 지시로 이해했습니다.

클라이언트 배포 버전 자주 변경되거나, 서버 버전 변경되면 관리하기 힘들겠다. OPS_CLIENT_KEY 관련해서는 콘솔 OPS 에서 생성, 재발급, 폐기 상태를 알 수 있게 관리 메뉴 '연락처/단축번호' 에 잘 구성해서 만들자. 그리고 Astrisk 환경변수에 적용 (수정,삭제,추가) 관리하는 연동이 필요한 부분은 Asterisk CLI 으로 추가하고 사용 절차 안내서를 만들자.

특히, 관리측면에서 정책을 만들어보자.

1. 콘솔 OPS 에서 클라이언트 인증 키(OPS_CLIENT_KEY), 연락처 정보, 빠른 연결 정보 관련해서는 macOS, 안드로이드, windows, iPad, iOS 등에 배포버전에 자동으로 들어가게 만들고, 사용자가 수동으로도 OPS_CLIENT_KEY를 입력하여 인증 받을 수 있게 한다.

2. Client 는 서버의 환경정보가 변경되었는지 갱신이 필요하면 이를 새정보 반영할 것을 표시해준다. 업데이트 필요. 현재 버전, 새버전 기능 정보 안내.


너의 검토 의견을 제시한다.

요지
방향(웹 수정→Asterisk·클라이언트 자동 반영, 키/연락처 통합관리, 버전·설정 변경 안내)은 타당하나, 영속 반영 방식·인증키 모델(전역/내선별)·배포 번들 범위·보안을 먼저 확정해야 운영 복잡도를 실제로 낮출 수 있습니다.
1. 영속 반영(/run/asterisk 휘발)·Asterisk CLI/서비스 반영
- 현황: 런타임 reload는 즉시 반영되나 재생성 시 템플릿+env(SIP_PASSWORD_*)로 초기화됨.
- 검토: Ops 메뉴(Asterisk CLI/서비스 작업)에서 “반영/영속화”를 제공하는 건 맞는 방향. 다만 “CLI 명령 추가”만으로는 env 파일·재생성까지 보장되지 않음.
- 권고:
- *단일 소스(Single Source of Truth)*를 Ops DB(연락처/회의실/SIP비밀번호)로 두고, 기동 시 DB→설정 렌더(또는 env 동기화)하도록 전환. 재생성 후에도 DB 기준 복원.
- Ops에 적용(런타임 reload) / 영속 반영(설정 저장+재생성 필요 시 안내·실행)를 분리. 재생성·다운타임은 활성통화 가드·유지보수 창·감사로그·롤백(이전 설정 스냅샷) 필수.
- 환경변수 직접 치환은 배포별(deploy/dev|prd/.env) 차이·권한 이슈가 있어, DB+렌더 파일/관리 볼륨 방식이 더 안전.
- 사용 절차 안내서(언제 적용/영속 반영/재생성, 차단 조건, 장애 시 롤백) 작성 필요.
2. OPS_CLIENT_KEY 관리(연락처/단축번호 내 구성)
- 현황: OPS_CLIENT_KEY는 서버 전역 공유키(요청 헤더 검증)로, 인증 성공 시 /api/client/contacts가 SIP 비밀번호까지 반환하는 구조.
- 검토: “연락처/단축번호 메뉴에 키 생성·재발급·폐기·상태”는 운영성에 유리. 다만 전역키 vs 내선(또는 기기)별 키를 구분해야 함.
- 전역키: 관리 단순, 누설 시 전체 영향·폐기/재발급 때 전 클라이언트 재설정 필요.
- 내선/기기별 키(권고): 해당 내선 연락처 행에 키/상태(활성·폐기·만료)/발급·재발급 이력 관리, 키가 내선에 바인딩되어 자기 내선 정보·비밀번호만 조회 가능하게 제한 → 유출 영향 최소화.
- 권고: 연락처 항목에 클라이언트 키 필드/상태·발급·재발급·폐기 UI를 두되, 평문 재노출 금지(생성/재발급 시 1회 표시·복사), 서버엔 해시 저장, 감사로그 기록. “키 입력/재발급” 안내를 같은 화면에 제공. (전역키를 유지할 경우엔 연락처가 아닌 서비스 설정 성격이라 ‘연락처 내 관리’와 개념 충돌이 있으니, 내선별 키 모델로 정리 권장)
3. SIP 비밀번호 자동 동기화
- 검토: Ops 연락처 값을 기준으로 인증된 클라이언트에 동기화해 바로 접속하게 하는 건 목적에 부합.
- 주의: 현재처럼 응답에 비밀번호를 싣는 방식은 TLS 미적용+공유/약한 키에 취약. 내선별 키+전송 암호화(내부라도 WSS/HTTPS/TLS 또는 최소 전용망) 전제 시 “연락처 기준 자동 반영” 운영 가능. 키 폐기 시 해당 클라이언트 동기화/접속 차단 정책도 함께 정의 필요.
4. 정책 1 — 배포본 자동 포함 + 수동 키 입력(멀티플랫폼)
- 검토: 연락처/빠른연결은 서버 조회로 이미 동적 반영 가능하므로 “번들 고정”보다 기동 시 동기화가 관리에 유리. 키를 배포본에 자동 포함하면 편하지만 설치본 추출 시 키 노출·버전별 키 파편화 위험.
- 권고(운영 절충):
- 배포본에는 *부트스트랩 정보(서버 주소/OPS URL, 선택적 기본 전역키-환경 한정)*만 포함, 실제 인증은 내선별 키(또는 발급키) 수동 입력/프로비저닝으로 전환.
- 엔터프라이즈 배포(macOS 프로파일/MDM, Android managed config, Windows/iOS 구성)로 키 주입은 가능하나 내선별 발급과 결합해야 의미 있음.
- “전 플랫폼 배포본에 동일 키 자동 포함”은 초기 편의는 있으나 보안·재발급 비용이 커서, 기본값 번들(옵션)+수동 입력/재발급 지원의 2트랙을 권장.
5. 정책 2 — 서버 설정/버전 변경 감지·업데이트 안내
- 검토: 매우 필요. 서버 주소·연락처뿐 아니라 클라이언트 호환 버전/기능 변경을 알려야 지원 비용 감소.
- 권고:
- 서버 GET /api/client/config(또는 별도 manifest)에 config schema/etag(갱신 필요 여부), min_supported/client_latest 버전, 릴리스 노트·필수/권장 업데이트 플래그 포함.
- 클라이언트는 주기/로그인/수동갱신 시 비교해 “업데이트 필요/설정 갱신 필요” 배지 + 현재/최신 버전·변경 기능 안내 표시. (이미 서버설정 갱신 흐름 있으므로 확장 용이)
- 호환성 깨지는 변경은 min_supported_version 미만 차단/강력 안내 정책 필요.
